# RTT 고정점 거리 실험 결과 (fps-text-v2)

실행일: 2026-09-19. 계획은 [abs_PLAN.md](abs_PLAN.md), 실행 설계는 [abs_EXPERIMENT.md](abs_EXPERIMENT.md)를 따른다. 모든 수치는 GLM-5.3 Flash(z-ai/glm-5.3-flash, reasoning_effort low, temperature 0.6, top_p 0.95), 이 프롬프트, v1/data의 15문제에서 관찰한 값이며 언어 자체의 거리로 일반화하지 않는다.

## 2. 사전 점검

기준 코드 45개는 모두 13케이스를 통과했다. 상태 해시는 CRLF, CR, LF를 같게 보고 공백 한 칸 차이를 구별했다. 분석기 점검(45개 기준 코드에 같은 종류의 변화를 적용)에서 원본 대 원본은 모두 1.0, 실제 코드의 NA는 0건이었다. 공백, 주석, 연산자, 줄 삭제에 대한 언어 간 평균 차이는 0.05 미만이었다.

식별자 개명만 언어 간 차이가 컸다(C++ 0.79, Haskell 0.62, Prolog 0.76). Haskell 기준 코드가 짧아 식별자 하나가 차지하는 비율이 높기 때문으로 보고 theta 0.85를 유지했다. 대신 Haskell 출발 경로는 같은 정도의 코드 변화에서도 theta 도달이 불리할 수 있다는 한계를 둔다. text 모드는 연산자 변경에 거의 반응하지 않았다(평균 0.99 이상). 따라서 Sym은 텍스트 안정성 기준일 뿐이고 기능 보존은 13케이스 평가가 따로 보장한다. 세부 기록은 artifacts-commandcode/fps-v2/preflight/PREFLIGHT.md에 있다.

## 3. 파일럿과 설계 동결

파일럿의 주 결과는 성공 3/90(모두 cpp-via-haskell)이었다. 등록된 진행 조건은 본 실행 예상 비용 $30 이하였고, 실측으로 추정한 비용이 $0.34라서 조건을 충족했다. 파일럿에서 바닥 효과를 확인했지만 추출 규칙, theta, 온도는 바꾸지 않고 설계를 동결했다(main_design.json). 파일럿 결과를 보고 규칙을 바꾸면 사후 조정이 되기 때문이다. 파일럿 90건은 D4에 따라 본 실행에 그대로 포함했다.

러너 변경은 한 가지뿐이다. 파일럿 전에 `--shard i/k` 병렬 옵션을 추가했다. 샤드별 비용 장부를 따로 두고 샤드마다 상한 30/k를 적용한다.

6개 H2 경로의 P_sf 순위는 세 임계값에서 같다. H1 묶음에서는 0.90에서 Python과 Java의 순서가 바뀐다(0.693 대 0.707). 대조 경로가 처리 경로보다 높다는 결론은 세 임계값 모두에서 유지된다.

파일럿 3문제를 뺀 12문제 분석에서도 결론은 같다. P_sf는 python 0.800, java 0.700, haskell 0.167, prolog 0.033이다. 대조 - 처리 Bonferroni 구간은 [0.358, 0.867], [0.533, 0.933], [0.300, 0.792], [0.417, 0.900]으로 모두 0을 포함하지 않는다. IPOP 6문제와 LeetCode 9문제로 나눠도 대조가 높은 방향은 같다.

## 7. 진단: 무엇이 P_sf를 결정했나

생성 언어별 편도 번역의 기능 통과율(해당 방향 단계 중 13케이스 전부 통과 비율):

| 생성 언어 | 통과율 범위 (경로별) |
| --- | --- |
| C++ | 98.0% ~ 100% |
| Python | 100% (270/270) |
| Java | 95.9% (208/217) |
| Haskell | 73.1% ~ 89.7% |
| Prolog | 36.0% ~ 46.0% |

1. P_sf 차이의 대부분은 기능 실패에서 나온다. 기능 실패가 없던 시도 중 성공한 비율은 python 62/74(0.84), java 56/67(0.84), haskell 13/19(0.68), prolog 2/4다. 처리 경로가 여전히 낮지만 표본이 작다. 반면 기능 실패 수는 1, 8 대 56, 71로 차이가 크다. 성공하려면 중간 언어 생성이 여러 번 연속으로 통과해야 하므로, 이 모델의 Haskell, Prolog 생성 능력이 P_sf를 직접 제한한다. 따라서 이번 결과에서 패러다임 차이의 효과와 언어별 모델 성능을 분리할 수 없다(abs_PLAN.md 1장의 해석 제한 그대로).
2. 기능이 보존된 복원 코드끼리 비교해도 처리 경로의 텍스트 변동이 크다. 인접 복원 Sym 중앙값은 python 0.64, java 0.62, haskell 0.24, prolog 0.16이다. 0.85 이상인 비율은 30%, 30%, 10%, 5%, 0인 비율은 7%, 5%, 28%, 32%다. 다른 패러다임을 거친 복원 C++가 매 왕복마다 더 크게 바뀐다는 관찰은 가설과 같은 방향이다. 다만 이 역시 모델의 언어별 성능과 분리되지 않는다.
3. 성공의 상당수는 똑같은 코드의 재생성이다. 성공 시점 Sym이 1.0인 시도가 python 17/62, java 31/56, haskell 7/13이다. temperature 0.6에서도 같은 코드로 돌아오는 경우가 theta 도달의 주된 경로 가운데 하나다. 상태 재등장 단계 수(python 54, java 36, haskell 8, prolog 0)도 같은 경향을 보인다.
4. 코드 추출 실패는 모두 한 응답에 코드 블록을 여러 개 낸 경우였다(초안 뒤에 "Wait" 같은 문장과 수정본을 붙임). 본 실행 H2의 format_error 124건 가운데 106건이 Prolog 생성 단계였다. 사전 규칙대로 기능 실패로 셌다. 사후 진단으로 마지막 블록만 평가하면 65/124(Prolog 52/106)가 13케이스를 통과했다. 규칙을 바꿨다면 Prolog 생성 통과율은 약 38%에서 50% 안팎으로 오르는 정도로 추정되며, 결론의 방향은 바뀌지 않는다. 이 진단은 주 결과에 반영하지 않는다.
5. 상한 초과는 대조 경로에서 많았다(12, 11건). 기능이 보존되는 만큼 왕복을 오래 이어가다 FPS 10을 넘긴 경우다. haskell-via-cpp도 18건으로 많았는데, Haskell 코드가 짧아 Sym이 낮게 나오는 분석기 특성(2장)의 영향일 수 있다.

## 8. 해석과 한계

- 이 모델과 설정에서 C++ 출발 RTT는 Python, Java를 거칠 때 제한 내 근사 고정점에 훨씬 자주 도달했다(P_sf 0.75~0.83 대 0.03~0.17). 도달한 시도의 d_n은 대조 경로가 약 1 작은 방향이지만 통계적으로 확인되지 않았다.
- 이 차이는 "패러다임이 다를수록 거리가 길다"는 가정과 같은 방향이다. 그러나 주된 기제는 중간 언어의 생성 실패이고, 이는 모델의 Haskell, Prolog 능력과 분리되지 않는다. Python, Java는 명령형이면서 학습 자료가 가장 많은 언어이기도 하다. 따라서 이 결과를 패러다임 자체의 거리로 해석하지 않는다.
- Prolog가 들어간 H2 경로는 바닥 효과 때문에 방향 비대칭이나 d_n을 비교할 수 없다.
- JPlag text Sym은 연산자 변화에 둔감하고 짧은 코드에서 불리하다. theta 도달은 코드 텍스트 안정성의 조작적 기준이며 의미 동일성을 뜻하지 않는다.
- N=5 반복은 같은 문제 안에서 서로 독립이 아니므로, 모든 구간은 문제 단위 부트스트랩(15문제)으로 계산했다. 문제 수가 적어 구간이 넓다.

## 9. 후속 설계 버전 후보 (미실행)

아래는 새 설계 버전으로만 실행할 수 있으며, 이번 결과를 바꾸지 않는다.

1. 추출 규칙: 코드 블록이 여러 개면 마지막 블록을 쓰거나, 프롬프트에 자기 수정 금지를 명시한다.
2. 상위 모델 GLM-5.3로 H1 네 경로를 재실행한다. 언어별 생성 능력이 높아지면 기능 실패의 교란이 줄어드는지 본다.
3. 기능 실패와 Sym 수렴을 분리해서 보고하는 조건부 지표를 사전 등록한다(예: 기능 실패 없는 시도 중 도달률).
4. 문제 수를 늘려 d_n 비교의 공통 성공 문제를 확보한다.
