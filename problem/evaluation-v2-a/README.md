## 검사 결과

- 문제별 고유 입력 10개, 총 190개. 같은 문제 안에서 공백을 정규화한 토큰 열의 중복은 0건이다.
- 기존 입력 파일 전체와 문제 본문의 모든 입력 예제를 제외했다. 해당 파일의 경로·해시는 [manifest.json](manifest.json)에 기록했다. 괄호 문제는 묶음 안의 개별 문자열도 기존 예제와 겹치지 않는다.
- 두 독립 계산 방식의 정답 대조 또는 하노이 이동 검증: 190/190 통과.
- 현재 `corpus/solutions/IPOP_*/reference.cpp`를 GCC 15.2.0, C++17, `-O2`로 컴파일하여 실행: 190/190 통과. 문제별 기준 코드 해시는 [validation_report.json](validation_report.json)에 있다.
- 고정한 저장소의 대응 JavaScript 풀이 추가 검사: 30/30 통과.
- 입력·정답은 UTF-8, LF이며 출력 비교는 공백 토큰 단위다. 컴파일 및 개별 C++ 실행 제한은 30초다.

하노이는 생성한 이동열을 별도의 상태 시뮬레이션으로 검증하고 이동 횟수가 `2^N-1`인지 확인한다. 이는 두 번째 이동열 생성기가 아니라 합법성·최소성 검사기다.

## 재검증

프로젝트 루트에서 실행한다. Python 표준 라이브러리, Node.js, C++17 컴파일러가 필요하며 모델 API는 호출하지 않는다. 검증 스크립트의 assertion을 유지하기 위해 Python의 `-O` 옵션은 사용하지 않는다.

```powershell
python problem/evaluation-v2-a/tools/validate_dataset.py
```

기본 컴파일러는 `.tools/gcc/bin/g++.exe`, 외부 소스는 `.tools/leetcode-source`다. 다른 위치라면 다음과 같이 지정한다.

```powershell
python problem/evaluation-v2-a/tools/validate_dataset.py --compiler "C:/path/to/g++.exe" --upstream "C:/path/to/Leetcode"
```

외부 소스 재수집은 [수집 안내](../leetcode-source/README.md)를 따른다. 검증기는 입력·정답, 생성기, 독립 검증기, 예시 제외 근거, 대응 JS 파일의 해시가 달라지면 중단한다. 실행 결과는 `validation_report.json`을 갱신하며 현재 기준 코드 해시를 새로 기록한다. 기존 보고서를 보존하려면 실행 전에 별도 복사한다.

입력 생성 코드는 [build_dataset.py](tools/build_dataset.py), 독립 정답 계산은 [oracles.py](tools/oracles.py)다. 생성기를 다시 실행하면 입력·정답·manifest를 덮어쓴다. 데이터 변경이 필요할 때만 별도 버전으로 생성하고 전수 검증한다.

## 적용 범위

이 입력은 현재 로컬 문제 본문과 기존 fixture에 제시되지 않았다는 의미에서 미제시 입력이다. 공개 문제의 정형적 경계값을 포함하므로 모델 학습 데이터와의 비중복이나 공식 비공개 채점 데이터임을 뜻하지 않는다. 구조가 동형인 입력까지 중복으로 보지는 않는다.

대부분 작은 입력의 완전탐색을 가능하게 설계했다. 값·길이·좌표 등의 일부 상한은 포함하지만 모든 문제의 최대 크기와 시간 복잡도를 검증하는 성능 시험은 아니다. 예를 들어 N-Queen은 기존 예제 N=8을 제외한 N=1..11의 10개 값, 하노이는 기존 예제 N=3을 제외한 N=1..11의 10개 값을 사용한다.

평가 입력·정답과 실패 진단을 번역 프롬프트에 전달하지 않는다. 기존 프롬프트는 유지하고 평가 로더에서 이 디렉터리를 별도 로딩해야 한다. 이번 자료 생성으로 프롬프트 분리 기능이나 v2 전체 준비 조건이 자동 충족되는 것은 아니다.
