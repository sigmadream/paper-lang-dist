## N01 원인 해결 확인

`hops_experiment.py:492`에서 `clock_abort.json`의 존재를 시계 신뢰 불가 상태로 읽고, `:505`에서 역행을 처음 감지하면 반복 진입과 조기 중단보다 먼저 해당 표식을 원자적으로 저장합니다. 이후 단조 시각이 예전 체크포인트 이상이 되어도 표식이 남아 있으면 새 요청을 허용하지 않습니다. 최종 `observation.json` 저장과 독립된 표식이므로 이전 결함의 저장 순서 의존성을 제거하였습니다.

기존 fixture와 모의 공급자를 사용하되 새 N01 테스트 함수를 호출하는 대신 별도의 실행 흐름을 구성하였습니다. 단조 시각을 `SimpleNamespace`의 모의 시계로 대체하고, 저장된 기존 단계가 한 홉인 경우와 두 홉인 경우를 각각 재현하였습니다.

1. 시각 100에서 기존 단계·응답·decision을 실제 임시 파일에 저장한 직후 충돌시켰습니다. 다음 단계의 응답·처리 캐시는 없는 원래 N01 조건입니다.
2. 시각 0에 재개한 뒤 최종 관측 저장 직전에 다시 충돌시켰습니다. 최종 관측은 없지만 clock_abort 표식과 중단 사유가 남아 있고 추가 공급자 호출은 0건이었습니다.
3. 시각 101에서 같은 최종 저장 충돌을 반복하였습니다. 예전 체크포인트 100보다 커졌어도 중단 사유는 `observation_clock_unavailable`이며 추가 호출은 계속 0건이었습니다. 표식 바이트도 변하지 않았습니다.
4. 시각 102에서 최종 저장을 허용하고 완성된 관측을 한 번 더 재개하였습니다. 관측·비용·임계치 결과가 동일하며 추가 호출은 없었습니다.
