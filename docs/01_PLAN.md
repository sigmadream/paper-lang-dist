## 3. 지표 계약: v1의 판정을 유지

- 경로는 C++ → X → C++이며 첫 왕복은 t=1이다. 정규화 해시는 공백·주석을 무시하되 식별자 변경은 구별한다.
- 후보 tau_c는 K=10 이내 최초 인접 복원 해시 일치 시점이다. 후보 도달 후 확인 c_max=5회를 수행하며 K는 확인 왕복을 포함하지 않는다.
- SF(c)는 후보가 존재하고, 후보 이전과 확인 c회까지 모든 중간·복원 단계가 테스트를 통과하며, 확인 중 후보 해시가 유지된 사건이다.
- c=0도 후보·기능 조건이 필요하다. 기능·형식·확인 해시 실패 후 종료하고 이미 관찰한 prefix로 c별 결과를 산출한다.
- p_SF(c)=성공(c)/평가 가능 관측 수, d_SF(c)=1-p_SF(c). 기능·출력 형식 실패는 분모에 남긴다. 원본 검증 실패·인프라 중단·미완료는 제외하고 수를 공개한다.
- tau=tau_c와 Delta_0=1-s(원본, 후보)는 SF 성공 조건부로만 계산한다. 성공 0건은 tau/Delta_0를 0이나 K로 대체하지 않고 결측으로 둔다.
- Dice, 방향을 고정한 SequenceMatcher(autojunk=False), 식별자 추상화·연산자/리터럴 보존·단위 편집 비용의 AST TSED를 유지한다. AST 유사도는 max(0, 1-TED/max(노드 수))이다.
- c=5를 주 결과, c=1·2와 c=0..5의 변화를 보조 결과로 보고한다. 추가 확인이 평탄해도 이번 본 실험 도중 c를 줄이지 않는다.
- 단일 손실 L_lambda=tau(성공), K+lambda(실패)는 후속 민감도 제안이다. 이번 주 결과를 대체하거나 수학적 metric으로 주장하지 않는다.

세부 정의와 경계 처리는 [v1 지표 계약](v1/PLAN_v1_metrics.md)을 따른다. v2는 테스트 분리와 다조건 비교를 확장하며, 판정 자체를 바꿀 경우 별도 버전으로 분리한다.

## 4. G0~G1: 코퍼스 버전과 미제시 입력

### G0. 완료 자료와 현재 상태 분리

1. v1의 원본 응답·코드 스냅샷·fixture·조건 해시·채택 attempt를 보존한다.
2. 현재 원본과 과거 스냅샷의 차이를 목록화한다. IPOP_1158처럼 변경된 원본은 새 버전의 변경 이유와 diff를 기록한다.
3. v1 요약 수치는 통합 JSON 및 결과 표와 대조한다. sequence 중앙값은 C 0.202, Java 0.155, Python 0.292이다.
4. v2에서 사용할 코드·의존성·코퍼스·설정의 스냅샷과 체크섬을 별도로 만든다.

G0 통과 기준: 변경 파일·이유·버전의 매핑이 있고, v1 기록이 변하지 않았으며, 요약 수치가 원본 집계와 일치한다. 이번 문서 갱신은 새 코퍼스 검증이나 모델 실행의 완료를 뜻하지 않는다.

### G1. 예시와 평가 입력 분리

- 각 문제를 prompt_examples와 evaluation_tests로 구분한다. 평가 입력·정답·실패 진단은 번역 프롬프트나 수정 재요청에 전달하지 않는다.
- v2-a는 기존 검증 통과 19문제 각각에 예시와 다른 고유 평가 입력을 최소 10개 마련한다. 통상·경계·오류를 유발하기 쉬운 유효 입력 범주를 가능한 한 3종 이상 포함하고 문제별 적용 가능성을 기록한다.
- 바이트 중복뿐 아니라 공백 정규화 등 입력 파서 관점의 중복도 점검한다. 해시, 입력 개수, 고유 개수, 예시와 겹침, 생성 seed를 문제별로 저장한다.
- 입력은 문제 명세와 제약에서 생성한다. 명세상 유효한 입력만 주 평가에 사용하고, 불법 입력 검사는 별도 강건성 항목으로 분리한다.
- 정답은 독립 기준 구현 또는 작은 입력의 완전탐색 등으로 교차 확인한다. 원본 코드 하나의 출력만 정답 근거로 삼지 않는다. 비결정 출력은 허용 정답 검사기를 고정한다.
- 원본은 예시·평가 입력 모두 통과해야 한다. 실패 문제는 번역 전에 모든 경로에서 제외하고 이유를 기록한다. 기준 미충족 상태로 본 실험을 시작하지 않는다.
- IPOP_1260은 v1 제외 상태를 유지한다. 수정해서 사용하려면 별도 문제 버전과 검증 근거를 만들고 19문제 비교 집합에 조용히 편입하지 않는다.
- 예시 내용과 순서는 v1과 가능한 한 유지하되 변경 사항을 명시한다. 테스트 결과를 보고 특정 실패만 구제하도록 입력·시간·헤더를 수정하지 않는다.

v2-b는 v1 및 모델/프롬프트 조정용 예비 문제와 겹치지 않는 새 50문제를 목표로 한다. 문자열, 탐색, 정렬·수치, 동적 계획법, 그래프 등 유형별 목표 수와 선정 seed를 사전 고정한다. 중복 구현·문제 변형도 점검한다. 50개를 확보하지 못하면 시작 전에 범위와 기대 정밀도를 다시 명시한다.

MultiPL-E 등 외부 벤치마크를 사용할 경우 함수 호출형 과제와 현재 stdin/stdout 실행기의 차이를 먼저 검증한다. 사용 조건, 출처, 버전, 정답 검사기, 래퍼의 타입·I/O 변환을 기록한다. 공개 문제라는 이유만으로 학습 오염이 없거나 은닉 테스트가 확보되었다고 보지 않는다.

G1 통과 기준: 모든 채택 문제에 입력 분리·중복 검사·정답 근거·원본 실행 결과가 있고 corpus_manifest가 동결되어 있다. v2-a 입력을 준비하지 못한 문제는 원인 공개 후 규모를 사전 재설계하며, 실행 중 교체하지 않는다.

| 프롬프트 선택 | 현재 템플릿을 기준으로 P1/P2 선택 기능과 실제 내용 해시 구현 |

동일 언어 대조군은 이번 최소 실행 규모에 포함하지 않는다. 기존 v1 CLI가 새 설정 필드를 지원한다고 가정한 실행 명령을 배포하지 않으며, 파서·실행·리포터 검증 후 사용법을 작성한다.

| AST 제한 | 5,000노드 / 30초 / 512 MiB | 측정률·최대 자원 확인 후 공통 설정 동결 |

v2-a의 순차 스케줄은 v1의 run 병렬도 3과 다르다. 강화 입력뿐 아니라 원본·스케줄·환경 변경도 포함될 수 있으므로 v1-v2 차이를 테스트 강화의 단독 인과 효과로 해석하지 않는다. 병렬 실행을 채택하면 예비 단계에서 다시 측정하고 조건 해시에 포함한다.

예비 실행은 v2-a에서 5문제 × 3경로 × 1회 = 15건, v2-b에서 별도 5문제 × 3경로 × 2모델 × 2프롬프트 × 1회 = 60건을 제안한다. 모델·프롬프트를 조정한 예비 결과는 본 실험에 합산하지 않는다.

G2 통과 기준: 설정 선택·평가 분리·재개·실패 경계·집계의 관련 테스트 통과, 각 조건의 예비 실행/감사, 조건별 호출 시간·토큰·절단·실행·AST 비용 측정이 완료되어 있다. 최종 모델 ID, P2 내용, 문제 목록, 출력·컨텍스트·복구·총비용 상한을 동결 파일에 모두 채운다.

## 6. G3~G4: 단계별 실행 규모와 예산

| 단계 | 제안 규모 | 관측 수 | 최대 논리 호출 수 |
| :--- | :--- | ---: | ---: |
| v2-a 예비 | 5 × 3경로 × 1모델 × 1프롬프트 × 1회 | 15 | 450 |
| G3: v2-a 본 실험 | 19 × 3 × 1 × 1 × 3 | 171 | 5,130 |
| v2-b 예비 | 5 × 3 × 2 × 2 × 1 | 60 | 1,800 |
| G4: v2-b 본 실험 | 50 × 3 × 2 × 2 × 3 | 1,800 | 54,000 |

호출 상한은 관측 수 × 2(K+c_max)=관측 수 × 30이다. 조기 실패는 실제 호출을 줄일 수 있으나 예산은 상한과 예비 실측을 함께 보고한다. 3회 반복은 각각 19개/50개의 독립 문제 수를 늘리지 않는다.

- 호출당 일시적 API 오류 재시도는 최대 3회(총 4시도)를 기본안으로 한다. 이때 본 실험의 API 시도 상한은 v2-a 20,520회, v2-b 216,000회이다.
- 실험 단위당 동일 조건 resume은 최대 2회로 제한한다. 완료한 단계를 재호출·중복 집계하지 않는다.
- 복구 불가능한 인프라 중단에 한해 새 attempt를 최대 1개 허용하는 정책을 검증한다. 새 attempt가 모두 처음부터 재실행되는 최악의 경우 위 시도 예산은 추가로 최대 2배이며, 시간·토큰 예산에 포함한다.
- 기본 벽시계 상한안은 v2-a 본 실험 전체 24시간, v2-b 각 모델×프롬프트 조건 24시간(4조건 총 96시간)이다. 예비 측정으로 가능성을 확인하고 시작 전에만 조정한다.
- 예비에서 측정한 입력/출력 토큰·평균과 꼬리 지연으로 조건별 예상 시간과 최대 예산을 작성한다. 과거 83.09분을 새 코퍼스·모델로 그대로 환산하지 않는다.
- 외부 API를 쓰는 경우 단가·토큰 예산을 확인해 총비용 상한을 동결한다. 아직 모델을 선택하지 않았으므로 가격이나 총액을 확정값으로 쓰지 않는다.

G3 통과 후에만 G4로 확대한다. 시간·비용 상한 초과, 입력 누출, oracle 오류, 조건 해시 변경이 발견되면 새 호출을 중단하고 상태를 보존한다. 고정된 종료 규칙에 따른 기능 실패는 정상적인 관측이며 반복 실행해 성공으로 대체하지 않는다.

시작하지 못한 관측과 인프라 미해결 건은 실패로 채우지 않고 진행률·분모·이유를 공개한다. 예정된 관측이 남아 있으면 완료 표시를 하지 않는다. 규모 변경은 기존 실험을 임의로 완료 처리하는 대신 개정 버전과 사유로 남긴다.

## 7. G5: 통계 분석과 해석 규칙

### 7.1 주 결과와 비교 단위

- 모델×프롬프트×코퍼스 버전별 p_SF/d_SF(c=5), 실패 범주, 분모·제외 수를 보고한다.
- v2-b의 같은 문제에 속한 모든 경로·모델·프롬프트·반복을 함께 재표집하는 문제 단위 대응 부트스트랩을 사용한다. 기본 2,000회와 seed=20260911을 사전 고정한다.
- 주 경로 비교는 3쌍이며 각 모델×프롬프트 조건별로 보고한다. 조건 전체 12개 차이 구간을 동시 해석할 경우 사전 정의한 동시 구간/다중비교 보정을 적용하고, 개별 95% 구간만으로 전체 순위를 단정하지 않는다.
- 구조적 결측과 인프라 제외 때문에 짝이 깨지면 원인·공통 평가 가능 문제 수를 보고한다. 전체 평가 가능 결과와 완전 대응 부분집합 결과를 구분한다.
- 문제 수 50이라는 목표가 검정력을 보장하지 않는다. 예비 변동성과 관심 효과 크기에 따른 예상 구간 폭을 G2에서 산정하고, 본 실험 결과를 본 뒤 유리한 시점에 중단하지 않는다.

### 7.2 성공 조건부 구조와 공통 집합

- c=5 성공의 tau·Delta_0 중앙값, Q1/Q3, n, AST 측정률·제외 이유를 기본 표로 유지한다.
- 각 모델·프롬프트 안에서 세 경로가 모두 성공한 동일 (문제, run) 교집합을 별도 비교한다. 교집합의 관측 수와 고유 문제 수, 빠진 문제 유형을 함께 보고한다.
- 부트스트랩에서도 해당 규칙으로 공통 집합과 대응 차이를 산출한다. n=0 또는 유효 재표집 부족은 결측으로 남긴다.
- 공통 집합은 문제 구성 차이를 줄이는 민감도 분석이며, 성공에 조건을 건 선택 편향 자체를 제거하지 않는다.
- tau 중앙값이 같다는 사실을 속도 분포의 동등성으로, 기능 통과와 큰 AST 변화 사례를 통계적 독립성으로 해석하지 않는다.
- AST·그래프·임베딩을 실패 예측에 쓰는 후속 분석에서는 성공 코드만 이용한 선택과 실패 후에야 얻는 정보의 누출을 점검한다.

### 7.3 확인 효과와 다모델 해석

- 추가 확인의 조건부 탈락률을 q_c=(성공(c-1)-성공(c))/성공(c-1)로 보고한다. 분모가 0이면 결측이다.
- c=2 대비 c=5의 추가 실패 수와 절감 가능한 호출·토큰을 계산한다. 실패를 조기에 중단한 실제 기록을 기준으로 하며 결측을 성공으로 채우지 않는다.
- 모델 비교는 같은 코퍼스·테스트·프롬프트 기준의 조건별 차이부터 제시한다.
- 보조 모형은 SF 성공 여부에 대한 혼합효과 로지스틱 모형으로 경로·모델·프롬프트, 경로×모델 상호작용, 문제별 임의 절편을 검토한다. 반복 의존성과 run 순서 효과도 설계에 맞게 진단한다.
- 모델 2개는 모델 모집단 분산을 추정하기에 제한적이므로 모델은 우선 고정효과로 비교한다. 완전 분리·수렴 실패·과적합 시 보조 모형의 한계를 보고하고 대응 기술통계를 우선한다.
- 조건부 기대 도달 시간, 단일 점수, 언어 군집은 주 분석을 대체하지 않는다. 군집을 만들더라도 척도·결합·방향성·재표집 안정성을 검증하고 역사적 계보와 구별한다.

## 8. v1 재평가와 버전 간 비교

강화 입력을 저장된 v1 코드에 적용하는 오프라인 감사는 별도 분석으로 가능하다. 원본·중간·후보·확인 코드 중 저장된 단계만 다시 실행하고 최초 실패와 새 입력 범주를 기록한다. 새로운 평가에서 더 일찍 실패했을 경로의 이후 기록을 실제 v2 실행 경로처럼 취급하지 않는다.

새 oracle과 v1 원본의 적합성을 먼저 검증하고, 모든 단계가 보존되었는지 확인한다. 결과를 원래 v1의 SF 통계에 덮어쓰거나 새 번역 실행과 합산하지 않는다. 테스트 강화에 따른 견고성 점검과 실제 재생성된 v2 성능을 별도 표로 둔다.

## 9. 산출물과 재생성 계약

다음은 생성할 산출물의 역할이며 현재 존재하는 파일이나 구현된 설정으로 간주하지 않는다. v2-a와 v2-b, 예비와 본 실험, 모델·프롬프트 조건을 경로와 메타데이터에서 분리한다.

| 산출물 | 필수 내용 |
| :--- | :--- |
| corpus_manifest / fixture_diversity | 문제 출처·버전·유형, 원본/입력 해시, 예시/미제시 구분, 고유 수·oracle 근거 |
| preflight / frozen_design | 원본 검증, 모델 ID, 프롬프트 실제 내용, 툴체인, 설정·순서·예산·제외 기준 |
| observations / iteration / attempts | 실행 단계·phase·실제 요청/응답·소스·테스트 집합 결과·해시·시간·토큰·채택 attempt |
| summary / completion_audit | 조건별 SF·분모·결측·실패, c별 단조성, 관측 유일성, 원본 대조 |
| paired_analysis / common_success | 문제 대응, 교집합 규칙·규모·제외, 부트스트랩·동시 구간·모형 진단 |
| RESULT_v2 / figures / regeneration_audit | 주 표·추이·조건부 분포·사례·한계, 고정 입력으로 결과를 재생성하는 절차 |

v1 실행 당시 코드와 새 리포터의 변경을 분리한다. 원본 응답과 통계를 바꾸지 않는 보고서 수정도 버전을 남긴다. c별 성공+실패=평가 수, 실패 범주 합, 성공 집합의 단조성, AST 결측 합과 실제 소스·응답 일치를 감사한다.

## 10. 단계별 완료 기준과 일정

| 단계 | 통과 기준 | 다음 작업 |
| :--- | :--- | :--- |
| G0 | v1 보존, 현재 변경 목록, 수치·버전 대응 확인 | 입력 분리 |
| G1 | 채택 문제의 미제시 입력·oracle·중복 감사와 원본 검증 통과 | 구현·예비 |
| G2 | 관련 테스트·예비 감사 통과, 모델·프롬프트·예산·설계 동결 | v2-a 본 실행 |
| G3 | 새 171건 계획의 종료·감사, 조건 변경·제외 공개 | v2-b 준비·예비 동결 |
| G4 | 동결된 교차 설계 완료·원본 응답 전수 감사 | 통합 분석 |
| G5 | 주·민감도 표, 한계, 재생성 및 논문 반영 검토 | 투고 준비 |

준비 작업은 G0~G1에 1주, G2에 1주를 우선 배정하는 잠정안이다. 모델 실행 기간은 예비 실측 후 산정하고, G3~G5는 실행 예산과 완료 기준으로 관리한다. 실패가 많아도 정상적으로 끝난 관측은 유효하며, 성공률이 낮다는 이유로 실험 설계를 바꾸지 않는다.

투고처·형식·마감은 미확정이다. 과거의 8월 출판 목표를 현재의 확정 일정으로 재사용하지 않는다. 연구 질문·실험 완료·공동 검토가 준비된 뒤 실제 제출 일정을 수립한다.
