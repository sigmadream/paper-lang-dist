##  모델 조건부, 실패 인지형 왕복 번역 측정

예상 제목: "실패와 구조적 안정화를 분리한 모델 조건부 프로그래밍 언어 왕복 번역 측정"

> "특정 모델, 번역 지침, 프로그램 집합, 검증 환경 아래에서 관찰되는 언어 간 왕복 번역의 기능 보존 및 구조적 안정화 특성"

이 정의는 연구의 의미를 축소하기 위한 것이 아닙니다. 오히려 무엇을 고정하고 무엇의 차이를 측정하는지 명확하게 하여, 결과를 재현하고 다른 조건과 비교할 수 있게 합니다. 이를 수식으로 표현하면, 한 번의 왕복은 다음 두 변환으로 구성됩니다.

$$
y_t \sim T^{m_f}_{A\rightarrow B}(\,\cdot\mid x_t),
\qquad
x_{t+1}\sim T^{m_b}_{B\rightarrow A}(\,\cdot\mid y_t)
$$

여기서 $m_f$와 $m_b$는 정방향과 역방향 번역 모델입니다. 같은 모델을 사용할 수도 있지만, 반드시 같을 필요는 없습니다. 중요한 점은 역방향 번역기가 정방향 번역기의 수학적 역함수라는 보장은 없다는 것입니다. 따라서 후속 원고에서는 $M^{-1}$보다 $T_{B\rightarrow A}$처럼 방향을 명시하는 표기가 해석상 안전합니다. 왕복 평가에서 정방향과 역방향 모델의 능력이 결합된다는 문제는 Allamanis 등의 RTC 연구에서도 한계로 논의됩니다. ([arXiv][1])

구조적 안정화와 의미 보존은 서로 다른 성질입니다. 모든 단계가 원본과 동일한 동작을 한다면, 의미만을 기준으로 보았을 때는 이미 같은 프로그램 동작을 유지하고 있는 것입니다. 이후의 반복 횟수는 그 의미를 "더 보존하게 되는 시간"이라기보다, 의미를 유지하면서 표현이 안정화되는 과정을 측정합니다. 따라서 핵심 개념은 "의미적 고정점" 하나보다 "기능 보존을 만족하는 구조적 근사 고정점"으로 정리하는 편이 더 명확합니다.

### 실패, 안정화, 미결정 상태를 분리해야 합니다

후속 실험에서는 각 시도의 종료 상태를 최소한 세 가지로 분리하는 것이 좋습니다.

| 종료 상태     | 판정 기준                          | 해석               |
| --------- | ------------------------------ | ---------------- |
| 기능 보존 안정화 | 기능 검증을 통과하면서 구조적 안정화 기준 충족     | 목표 상태에 도달        |
| 검증 실패     | 컴파일 오류, 실행 오류, 오답, 시간 초과 등으로 중단   | 번역 또는 실행 조건에서 실패 |
| 한도 내 미안정화 | 기능은 유지했지만 정해진 왕복 한도까지 안정화하지 않음 | 관찰 한도 내 결론 미도출   |

이 중 실패는 다시 원인을 나누어 저장해야 합니다. 특히 오답, 컴파일 오류, 시간 초과를 하나의 "의미 실패"로만 묶으면 원인 분석이 어려워집니다. 시간 초과는 알고리즘 변형이나 실행 환경의 영향을 포함할 수 있으므로 별도 결과로 남기는 것이 좋습니다.

반면 API 장애나 실행 서버 장애는 언어 번역 실패와 구분해야 합니다. 어떤 경우를 재시도하고 어떤 시도를 유효 분모에 포함할지도 실험 전에 정해야 합니다.

분석 방법으로는 안정화와 실패를 서로 다른 종료 사건으로 다루는 경쟁위험 분석을 적용할 수 있습니다. 실패로 종료된 시도를 단순히 "더 관찰하지 못한 시도"로 처리하는 것과, 별도의 실패 사건으로 처리하는 것은 다릅니다. 경쟁위험의 누적발생함수는 관심 사건이 다른 종료 사건보다 먼저 발생할 확률을 추정하는 방법입니다. ([Scikit-Survival][2])

### 하나의 거리값보다 측정 프로파일을 먼저 제안하십시오

첫 단계에서는 다음과 같은 측정값을 함께 보고하는 것을 권합니다.

$$
\mathcal{P}
=
\left(
P_{\mathrm{stable}},
P_{\mathrm{fail}},
P_{\mathrm{unresolved}},
H_{\mathrm{stable}},
\Delta_{\mathrm{origin}},
\Delta_{\mathrm{step}},
C
\right)
$$

각 항목의 역할은 다음과 같습니다.

* $P_{\mathrm{stable}}$: 기능을 보존하면서 안정화한 비율
* $P_{\mathrm{fail}}, P_{\mathrm{unresolved}}$: 실패 비율과 한도 내 미안정화 비율
* $H_{\mathrm{stable}}$: 안정화 성공 시의 홉 수 분포
* $\Delta_{\mathrm{origin}}, \Delta_{\mathrm{step}}$: 원본 대비 변화와 직전 단계 대비 변화
* $C$: 전체 번역, 검증 비용

특히 구조 변화는 다음 두 값을 구분해야 합니다.

$$
\Delta_{\mathrm{origin}}(t)
=
1-\operatorname{Sim}(x_0,x_t)
$$

$$
\Delta_{\mathrm{step}}(t)
=
1-\operatorname{Sim}(x_{t-1},x_t)
$$

직전 단계와 매우 비슷하다는 사실은 원본과도 비슷하다는 뜻이 아닙니다. 처음 몇 번의 번역에서 원본 구조가 크게 바뀐 뒤, 그 새로운 구조에서 안정화할 수 있기 때문입니다.

두 번째 원고의 JPlag 유사도는 인접한 복원 코드 사이의 값으로 정의되어 있습니다. 따라서 후속 실험에서는 원본 대비 변화량을 별도로 추가하면, "빠른 안정화"와 "높은 구조 보존"을 구분할 수 있습니다. 

또한 JPlag는 프로그램 사이의 유사성을 탐지하는 도구이므로, 이를 구조 변화의 관측 도구로 사용하되 기능적 동등성의 판정은 실행 검증으로 분리하는 것이 좋습니다. 정규화, 최소 일치 토큰 수 등의 설정도 결과에 영향을 줄 수 있어 버전과 함께 기록해야 합니다. ([GitHub][3])

### 기존 $(D=H/P_s)$의 해석을 검증하는 것 자체가 연구가 될 수 있습니다

현재 지표를 폐기할 필요는 없습니다. 대신 어떤 목적에 적합한 지표인지를 분명히 해야 합니다.

현재의 \(D\)는 성공 시 평균 홉 수를 성공률로 보정한 지수입니다. 다만 이를 "성공할 때까지 실제로 필요한 평균 번역량"으로 해석하려면, 실패 시도에서 소비한 비용도 고려해야 합니다. 

동일한 초기 프로그램에서 독립적이고 동일한 조건의 시도를 성공할 때까지 재시작한다고 가정하면, 기대 총비용은 다음과 같이 쓸 수 있습니다.

$$
C_{\mathrm{restart}}
=
\frac{\mathbb{E}[C_{\mathrm{attempt}}]}{P_s}
=
\mathbb{E}[C\mid S]
+
\frac{1-P_s}{P_s}\mathbb{E}[C\mid \neg S]
$$

이 식은 후속 연구에서 검토할 수 있는 비용 해석의 대안입니다.

예를 들어 성공 시 평균 6홉, 성공률 0.5인 두 설정은 기존 지표로 모두 \(D=12\)입니다. 하지만 실패한 시도가 평균 1홉을 소비하면 기대 재시작 비용은 7홉이고, 평균 9홉을 소비하면 15홉입니다. 즉, 실패가 언제 일어나는지를 무시하면 같은 거리값이 매우 다른 실무 비용을 나타낼 수 있습니다.

반대로 실제 비용보다 "제한된 예산 안에서 얼마나 빨리 안정화하는가"에 관심이 있다면, 다음과 같은 보조 지표를 시험할 수 있습니다.

$$
L_K
=
1-\frac{1}{K}\sum_{k=1}^{K}F_S(k)
$$

여기서 \(F_S(k)\)는 실패보다 먼저, \(k\)번 왕복 이내에 기능 보존 안정화에 도달할 확률입니다. 이 지표는 빠르고 자주 안정화할수록 작아집니다. 다만 이는 후속 실험에서 검증할 후보 지표이지, 이미 타당성이 확보된 언어 거리 정의는 아닙니다.

또한 관측 성공이 0건인 경우는 "이 조건과 표본에서 성공을 관측하지 못했다"는 뜻이지, 언어 사이의 실제 거리가 무한대라는 증거는 아닙니다. 이 경우 성공률의 불확실성과 관찰 한도를 함께 보고해야 합니다.

### 이 논문의 가장 중요한 검증 질문

이 후속 논문의 성패는 새로운 공식을 만드는 데만 달려 있지 않습니다. 다음 질문에 답해야 합니다.

> 반복 횟수와 구조 변화 정보를 추가하면, 단순한 번역 성공률만 사용할 때보다 독립적인 번역 실패나 수정 비용을 더 잘 예측할 수 있는가?

이를 검증하려면 비교 기준을 단순하게 잡는 것이 좋습니다. 편도 번역 성공률, 한 번의 왕복 성공률, \(P_s\)만 사용하는 기준, 기존 \(H/P_s\), 새 프로파일을 비교하십시오.

새 측정값을 계산하는 데 사용하지 않은 프로그램이나 테스트에서 예측력을 평가해야 합니다. 같은 JPlag 점수로 지표를 정의하고 다시 그 점수를 잘 예측한다고 평가하면, 유용성을 독립적으로 검증한 것이 되지 않습니다.

> Haskell과 Prolog를 경유할 때 실패가 증가하는 이유는 계산 모델의 차이 때문인가, 해당 언어에 대한 모델의 역량 때문인가, 아니면 인터페이스와 실행 환경 때문인가?

현재 원고는 계산 모델의 차이가 거리 증가에 반영되었다고 해석합니다. 다만 이 설명과 경쟁하는 다른 요인을 별도 실험으로 검증하면 연구가 훨씬 강해집니다. 

관련 근거로 MultiPL-T는 학습 자원이 적은 언어에 대해 테스트로 검증한 번역 데이터를 구성하고 모델을 개선하는 접근을 제시합니다. 따라서 특정 언어의 낮은 성능을 언어 자체의 구조적 어려움으로만 해석하기보다, 모델의 학습 경험과 번역 역량을 함께 고려해야 합니다. ([arXiv][4])

### 같은 문제를 다른 표현 방식으로 구현한 대응 코퍼스

문제 수만 늘리기보다, 동일한 기능을 서로 다른 방식으로 구현한 프로그램 쌍을 만드는 것을 권합니다.

예를 들어 같은 합계 계산이나 탐색 문제에 대해 반복문 중심 구현, 재귀 구현, 고차 함수 중심 구현을 준비할 수 있습니다. 입력과 출력은 동일하게 유지하고 표현 방식만 바꾸면, "어떤 언어가 어려운가"보다 "어떤 구조 변환이 어려운가"를 분석할 수 있습니다.

이때 특히 유용한 비교 대상은 다음과 같습니다.

| 비교할 프로그램 특성 | 대응 실험의 예            | 확인하려는 현상             |
| ----------- | ------------------- | -------------------- |
| 명시적 상태 변경   | 반복문, 누적 변수 구현과 재귀 구현 | 상태 전달 방식의 변환 부담      |
| 자료구조 갱신     | 배열 갱신과 새로운 리스트 구성   | 변경 가능한 상태의 재구성       |
| 제어 흐름       | 반복 탐색과 재귀 탐색        | 반복, 재귀 변환의 안정성        |
| 결과 표현       | 단일 결과와 복수 해의 명시적 열거 | 논리형 경로에서의 출력 계약 영향   |
| 라이브러리 의존성   | 직접 구현과 표준 라이브러리 호출  | 계산 구조와 API 지식의 영향 분리 |

원고에서 하노이탑은 Haskell, Prolog 경로에서도 초기 두 번의 왕복 동안 기능이 보존된 사례로 제시됩니다. 이는 재귀 구조의 영향을 검토할 좋은 출발점이지만, 하나의 사례를 일반화하기보다 같은 특성을 가진 여러 문제에서 반복 확인하는 것이 좋습니다. 

### 기준 언어 편향도 통제해야 합니다

C++로 작성된 프로그램을 모두 다른 언어로 옮기면, 연구 질문은 엄밀하게는 "C++식으로 표현된 문제 해결 방식을 다른 언어가 얼마나 잘 받아들이는가?"에 가깝습니다.

이를 보완하기 위해 일부 문제에서는 전문가 검토를 거친 Haskell 또는 Prolog의 자연스러운 구현을 시작점으로 사용하고, 반대 방향 왕복도 수행하는 것을 권합니다.

단, 모든 언어 쌍을 한 번에 확장하기보다는 C++↔Haskell 같은 핵심 경로에 먼저 적용하십시오. 시작 언어와 원본 코드의 표현 방식이 결과를 얼마나 바꾸는지 확인한 뒤 확장하는 편이 비용을 통제하기 쉽습니다.

### 작은 개입 실험으로 실패 원인을 좁히기

실험 조건은 기본 번역, 타입, 인터페이스 명시, 고정된 입출력 래퍼 제공, 제한된 컴파일러 피드백 제공 등으로 나눌 수 있습니다.

여기서 중요한 것은 피드백을 제공한 조건에 더 많은 호출과 토큰을 허용하면서, 기본 조건과 단순 성공률만 비교하지 않는 것입니다. 호출 수와 비용을 맞춘 대조 조건이 필요합니다.

타입 정보 활용의 근거로는 *Type-Constrained Code Generation with Language Models*가 있습니다. 이 연구는 타입 기반 디코딩을 형식화하고 TypeScript에서 구현, 평가했지만, 그 결과를 Haskell이나 Prolog에 바로 적용할 수 있다고 가정해서는 안 됩니다. 후속 연구에서는 우선 타입 서명과 컴파일러 진단을 이용하는 현실적인 개입부터 시작할 수 있습니다. ([arXiv][5])

또한 2026년 공개된 FPEval 연구는 Haskell, OCaml, Scala의 721개 과제에서 기능 정확성과 코드 스타일을 함께 평가하며, 명령형 패턴을 따르는 비관용적 함수형 코드 문제를 보고합니다. 따라서 후속 연구에서는 "실행에 성공했는가?"와 "대상 언어의 자연스러운 표현을 사용했는가?"를 분리하는 것이 차별화에 도움이 됩니다. ([arXiv][6])

## 세 번째 연구: 근사 고정점은 무엇을 의미하는가?

이 방향은 현재 연구에서 가장 독특한 요소인 반복과 고정점을 직접 심화합니다.

### 한 번의 높은 유사도를 안정화로 볼 수 있는가?

현재는 인접 복원 코드의 유사도가 0.85 이상이면 근사 고정점으로 판정합니다. 

후속 연구에서는 다음 세 판정 방식을 비교하는 것이 좋습니다.

단일 판정은 한 번 임계치를 넘으면 안정화로 처리합니다. 연속 판정은 두세 번 연속으로 기준을 충족해야 합니다. 재검증 판정은 안정화로 선언한 코드에서 독립적인 추가 번역을 수행하여 다시 변하거나 실패하는지 확인합니다.

이 비교를 통해 "고정점 도달률" 대신 더 구체적으로 안정화 선언 후 유지율을 평가할 수 있습니다. 특히 확률적 생성에서는 한 번 관측한 안정화가 이후에도 유지된다는 보장이 없으므로, 이 차이 자체가 중요한 연구 대상입니다.

### 원본의 특징이 사라지고 모델의 문체로 모이는가?

같은 기능을 수행하는 여러 원본 구현에서 왕복 번역을 시작한 뒤, 최종 코드가 몇 가지 구조로 모이는지 분석할 수 있습니다.

예를 들어 반복문 기반, 재귀 기반, 라이브러리 기반의 서로 다른 원본이 모두 유사한 C++ 코드로 바뀐다면, 다음 가설을 세울 수 있습니다.

> 관찰된 안정화는 두 언어의 공통 표현 구조뿐 아니라, 번역 모델이 선호하는 구현 방식에 의해 유도될 수 있다.

이를 검증하기 위해서는 같은 언어 안에서 재작성하는 대조군이 중요합니다. C++→C++→C++에서도 비슷한 구조 수렴이 나타나는지 확인하면, 언어 변환 없이도 발생하는 모델의 재작성 성향을 관찰할 수 있습니다.

다만 자기 언어 재작성 점수를 단순히 빼는 것만으로 "순수한 언어 거리"를 얻었다고 주장해서는 안 됩니다. 이는 모델의 기본 변형 성향을 확인하는 통제 실험으로 사용하는 편이 적절합니다.

### 오류 누적과 단순한 실패 기회 증가를 구분하기

원고는 반복 번역 과정의 오류 누적을 중요한 고려사항으로 제시합니다. 

여기에는 추가로 검증할 부분이 있습니다. 각 번역에서 실패할 확률이 일정하더라도, 번역을 여러 번 수행하면 한 번이라도 실패할 가능성은 커집니다. 따라서 왕복 횟수가 늘수록 전체 실패가 증가했다는 사실만으로 오류가 누적되었다고 결론 내리기는 어렵습니다.

후속 분석에서는 "지금까지 살아남은 코드가 다음 홉에서 처음 실패할 확률"이 단계에 따라 증가하는지 살펴보는 것이 좋습니다. 정방향과 역방향, 프로그램 난이도, 코드 길이 변화를 함께 고려하면, 반복 과정에서 코드가 실제로 더 취약해지는지 분석할 수 있습니다.

## 네 번째 연구: GNN으로 실패와 안정화를 조기에 예측하기

예상 제목: "프로그램 그래프 변화에 기반한 LLM 왕복 번역의 조기 실패 예측"

이 방향에서는 GNN을 곧바로 "의미 거리를 계산하는 모델"로 사용하기보다, 검증 가능한 번역 결과를 예측하는 모델로 사용하는 것이 좋습니다.

코드의 구문과 변수 사용 관계를 그래프로 표현하고 학습하는 접근은 *Learning to Represent Programs with Graphs*에서 제시되었습니다. 다만 그래프 표현이 유용하다는 사실과, 그래프 임베딩 사이의 거리가 곧 프로그램 의미 거리라는 주장은 구분해야 합니다. ([arXiv][7])

### 구체적인 예측 과제

가장 실용적인 질문은 다음과 같습니다.

> 원본 코드와 첫 한두 번의 왕복 결과만 보고, 이후 기능 실패 여부와 안정화 가능성을 예측할 수 있는가?

입력으로는 원본 C++ 코드의 AST, 제어 흐름, 데이터 흐름과 초기 왕복에서의 변화량을 사용할 수 있습니다. 출력은 제한된 예산 내 안정화 확률, 오답 발생 확률, 추가로 필요한 호출 수 등으로 설정할 수 있습니다.

초기 구현에서는 C++로 복원된 코드만 그래프로 비교하는 것을 권합니다. Haskell과 Prolog까지 하나의 공통 그래프로 직접 정렬하는 문제를 동시에 해결하려 하면 연구 범위가 크게 늘어납니다.

### GNN이 필요한지부터 검증해야 합니다

비교 기준은 코드 길이, 분기 수, 반복문 수 등의 단순 특징을 사용하는 로지스틱 회귀나 트리 기반 모델에서 시작하면 좋습니다. 그다음 토큰 기반 표현과 AST 기반 표현을 비교하고, 마지막으로 제어, 데이터 흐름 간선을 추가한 GNN을 평가하십시오.

이렇게 해야 그래프를 사용해서 좋아진 것인지, 단지 더 많은 정보를 넣어서 좋아진 것인지 구분할 수 있습니다.

또한 같은 문제의 다른 시드, 다른 원본 구현, 다른 왕복 단계가 학습 집합과 평가 집합으로 나뉘지 않도록 해야 합니다. 평가 분할은 개별 코드 파일보다 문제와 그 파생 구현의 묶음 단위로 설계하는 것이 좋습니다.

최종 평가는 정확도뿐 아니라, 조기 중단이나 모델 교체를 적용했을 때 성공률을 얼마나 유지하면서 실제 번역 비용을 줄였는가로 연결할 수 있습니다.


## 다섯 번째 연구: 구조 보존, 정확성, 비용에 따른 모델 자동 선택

이 방향은 첫 번째 원고의 결론에 제시된 자동 모델 할당 계획을 직접 구현하는 연구입니다. 

### "가장 좋은 모델"이 아니라 "요구사항에 맞는 모델"을 선택하기

모델 선택의 목적을 하나로 고정하지 않는 것이 중요합니다.

예를 들어 레거시 코드 검토에서는 원본 구조의 유지가 중요할 수 있고, 대상 언어로 장기 유지보수할 시스템에서는 자연스러운 구현 방식이 더 중요할 수 있습니다. 연구에서는 이러한 요구를 구조 보존 우선, 기능 정확성 우선, 비용 제한 등의 실험 시나리오로 명시할 수 있습니다.

선택기는 언어 쌍뿐 아니라 프로그램 특성, 필요한 정확성 수준, 허용 비용, 초기 번역 결과를 입력받도록 설계할 수 있습니다.

평가에서는 항상 하나의 모델을 사용하는 방식, 언어 쌍별 고정 모델 선택, 프로그램 특성 기반 선택, 초기 번역 결과를 이용한 적응적 선택을 비교하면 됩니다.

### 7.2 중간 언어를 경유하는 전략은 별도 검증이 필요합니다

직접 번역 \(A\rightarrow B\)와 중간 언어를 경유하는 \(A\rightarrow C\rightarrow B\)도 비교할 수 있습니다. 하지만 왕복 거리값을 간선 가중치처럼 더해 최적 경로를 찾는 방식은 바로 적용하지 않는 것이 좋습니다.

현재 지표에는 방향별 번역 역량, 시작 코드, 반복 과정이 함께 들어 있습니다. 따라서 왕복 거리의 합이 실제 다단계 번역의 난이도나 성공률을 나타낸다는 보장은 없습니다. 경로 선택은 별도의 편도 번역 실험과 비용 측정으로 검증해야 합니다.

외적 타당성을 높이는 다음 단계로는 소규모 저장소 수준의 번역이 적절합니다. RepoTransBench는 실행 가능한 테스트를 갖춘 저장소 수준 번역을 다루고, 번역 방향에 따라 난이도가 달라짐을 보고합니다. 이는 현재의 알고리즘 문제 기반 결과를 실제 소프트웨어로 확장할 때 참고할 수 있습니다. ([arXiv][8])

## 8. 장기 연구: 제한된 언어 부분집합에서 측정 개념을 형식적으로 검증하기

실험 기반 연구와 별개로, 작은 언어를 대상으로 이론적 토대를 만드는 방향도 유망합니다.

예를 들어 정수, 유한 리스트, 조건문, 제한된 반복과 재귀를 갖는 명령형, 함수형 언어 부분집합을 정의하고, 다음 질문을 연구할 수 있습니다.

의미 보존 번역과 구조적 고정점은 어떤 관계가 있는가? 정방향과 역방향 번역이 모두 의미를 보존한다고 해서, 왕복 코드가 구문적으로 더 이상 변하지 않는다는 결론이 자동으로 나오지는 않습니다. 고정점을 보장하려면 추가적인 정규화 규칙이나 변환의 성질이 필요합니다.

어떤 종류의 거리를 정의할 것인가? 현재의 \(H/P_s\)는 자기거리 0, 대칭성, 삼각부등식이 보장된 수학적 거리라고 보기 어렵습니다. 따라서 당장은 "거리 지수"로 사용하고, 엄밀한 거리 구조는 별도의 정의와 검증 과제로 분리하는 것이 좋습니다.

이론 연구에서는 범위를 제한한 실행 의미를 정의하고, 번역기의 의미 보존이나 정규화의 멱등성을 Rocq/Coq 등으로 검증하는 접근을 생각할 수 있습니다. 다만 이 결과의 적용 범위는 정의한 부분집합에 한정해서 보고해야 합니다.

이 방향은 첫 후속 논문에 모두 포함하기보다, 실험적으로 무엇을 측정하는지 정리한 뒤 그 정의를 이론적으로 검토하는 연구로 분리하는 것이 좋겠습니다.

| -------- | ---------------------------------- | ----------------- |
| 핵심 경로    | C++→Python, Java, Haskell, Prolog→C++ | 기존 결과와의 연속성       |
| 파일럿 코퍼스  | 약 30개 문제                           | 실패 유형과 호출 비용 파악   |
| 본 실험 코퍼스 | 약 100~200개 문제에서 시작                 | 표본 수보다 특성별 균형 우선  |
| 모델       | 서로 다른 계열 3개 정도                     | 모델 의존성과 상호작용 분석   |
| 반복       | 조건별 3~5회                           | 생성 변동성 관찰         |
| 관찰 한도    | 우선 최대 5회 왕복                        | 실행 비용 통제          |
| 확장 관찰    | 일부 표본만 더 긴 왕복 수행                   | 늦은 안정화와 안정화 유지 검증 |
| 통제 실험    | 동일 언어 재작성, 일부 교차 모델 왕복             | 모델 문체와 방향별 역량 분리  |

이 숫자는 검정력을 보장하는 기준이 아니라 파일럿을 시작하기 위한 설계안입니다. 실제 표본 수는 파일럿에서 관찰한 문제 간 편차와 실패율을 바탕으로 조정해야 합니다.

비용도 미리 계산해야 합니다. 예를 들어 200개 문제, 네 경로, 세 모델, 세 번 반복이면 7,200개 왕복 궤적입니다. 최대 다섯 번 왕복한다면 조기 종료를 고려하지 않은 상한은 72,000회의 편도 번역 호출입니다. 교차 모델 실험과 피드백 조건은 여기에 추가되므로, 우선 일부 표본에서 수행하는 것이 좋습니다.

### 9.2 기능 검증은 매 홉마다 원본 기준으로 수행하기

검증에서는 중간 언어 코드와 복원된 C++ 코드를 모두 확인해야 합니다. 최종 복원 코드만 통과하면, 중간 단계의 잘못된 변환을 역번역이 우연히 보정한 경우를 놓칠 수 있습니다.

또한 각 단계의 기대 결과는 직전 단계가 아니라 검증된 원본 또는 독립적인 정답 구현을 기준으로 해야 합니다. 직전 단계의 출력을 정답으로 계속 넘기면, 한 번 생긴 오류가 이후 단계의 기준으로 굳어질 수 있습니다.

샘플 입출력만으로 기능 보존을 판단하는 것보다, 경계값, 무작위 입력, 문제별 성질을 이용한 테스트를 추가하는 것이 좋습니다. EvalPlus는 테스트를 강화했을 때 기존에 통과하던 잘못된 코드를 찾아내고 모델 순위까지 달라질 수 있음을 보여줍니다. 따라서 테스트 강도에 따른 거리 순위의 안정성도 분석 항목으로 삼을 수 있습니다. ([arXiv][9])

다만 테스트 통과는 정의한 입력 집합에서의 기능 일치를 뜻합니다. 모든 입력에 대한 의미 동등성 증명과는 구분해서 서술해야 합니다.

### 9.3 통계 분석 단위

두 번째 원고는 15개 문제를 다섯 번 반복합니다. 이는 생성 시도의 수를 늘리지만, 서로 다른 문제를 75개 확보한 것과는 다릅니다. 

후속 분석에서는 문제별 결과를 묶어서 재표집하는 부트스트랩이나, 문제 차이를 고려하는 혼합효과 모형을 검토할 수 있습니다. 언어와 모델의 평균 효과뿐 아니라 언어×모델 상호작용이 얼마나 큰지도 확인하는 것이 중요합니다.

반복 횟수는 평균 하나보다 중앙값과 사분위 범위를 함께 보고하고, 성공률과 거리값에는 불확실성 구간을 제시하는 편이 좋습니다. 특히 성공이 거의 없는 경로에서는 순위와 배수 해석이 표본에 얼마나 민감한지 별도로 보여주어야 합니다.

### 9.4 재현성을 위해 반드시 남길 기록

각 홉의 원본, 생성 코드, 정방향과 역방향 모델 식별자, 프롬프트, 생성 설정, 컴파일러와 런타임 버전, 테스트 결과, 유사도 설정, 종료 이유, 토큰 사용량을 함께 저장하십시오.

초록에 적힌 모델 이름이나 사양만으로는 실험 시점의 정확한 호출 조건을 복원하기 어렵습니다. 실제 요청, 응답 메타데이터를 보존해야 후속 연구에서 모델 변경과 언어 효과를 구분할 수 있습니다.

## 10. 권장 논문 구성과 실행 순서

### 10.1 첫 번째 후속 논문의 중심 질문

첫 논문은 다음 네 질문으로 묶으면 좋겠습니다.

RQ1. 모델 의존성
언어별 왕복 번역 결과의 순위는 모델이 바뀌어도 유지되는가?

RQ2. 실패 처리의 영향
조기 실패를 분리하면 기존 반복 횟수 및 \(H/P_s\) 기반 해석이 얼마나 달라지는가?

RQ3. 안정화 정의의 강건성
유사도 임계치, 연속 판정 횟수, 왕복 한도를 바꾸어도 결과가 유지되는가?

RQ4. 추가적인 실용 가치
왕복 과정의 구조 변화와 안정화 정보가 단순 성공률보다 독립적인 실패, 수정 비용 예측에 도움이 되는가?

이렇게 구성하면 논문의 기여는 측정 정의, 평가 프로토콜, 강건성 분석, 외부 예측력 검증으로 정리됩니다. 언어 순위를 하나 제시하는 것보다 연구의 재사용 가능성이 커집니다.

### 10.2 약 12주의 작업 계획 예시

기존 번역 파이프라인을 재사용하고 실험 예산을 확보한다는 가정에서, 다음과 같이 나눌 수 있습니다.

| 기간     | 수행할 작업                          | 완료 기준              |
| ------ | ------------------------------- | ------------------ |
| 1~2주   | 표, 본문 수치 검증, 종료 상태 재정의, 로그 형식 정비 | 기존 결과를 동일 기준으로 재집계 |
| 3~4주   | 파일럿 코퍼스와 강화 테스트 구축              | 실패 유형, 비용, 판정 기준 확정  |
| 5~7주   | 다모델 본 실험과 핵심 통제 실험              | 홉별 코드와 검증 결과 확보    |
| 8~9주   | 임계치 민감도, 통계 분석, 추가 예측력 평가         | 연구 질문별 결과 도출       |
| 10~12주 | 사례 분석, 원고 작성, 재현 패키지 정리         | 제출 가능한 원고와 실험 산출물  |

이는 연구 작업량에 대한 계획이며, 논문 심사나 출판에 필요한 기간을 포함한 예상은 아닙니다.

### 10.3 이후 논문은 세 흐름으로 나누는 것을 권합니다

첫 논문은 측정의 타당성에 집중하십시오.
모델 조건부 측정, 실패와 안정화의 분리, 기존 지표와의 비교, 독립적인 예측력 검증이 중심입니다.

두 번째 논문은 실패 원인을 설명하십시오.
계산 모델별 프로그램 특성, 원본 표현 방식, 타입, 입출력 인터페이스, 피드백의 영향을 대응 실험으로 분석합니다.

세 번째 논문은 예측과 선택으로 연결하십시오.
축적한 왕복 궤적을 이용해 GNN 등의 예측기를 만들고, 실제 비용을 줄이는 모델 선택 또는 조기 중단 시스템으로 평가합니다.

## 종합 의견

현재 연구에서 가장 발전 가능성이 큰 부분은 "왕복 번역을 반복하면 코드가 어떻게 변하고, 언제 실패하며, 어떤 조건에서 안정화되는가"를 관찰할 수 있는 실험 구조입니다. 이를 곧바로 언어 자체의 절대적인 거리로 해석하기보다, 먼저 모델과 실험 조건이 명시된 측정 체계로 확립하는 것이 좋겠습니다.

따라서 다음 논문의 중심 주장은 다음과 같이 잡는 것을 권합니다.

> 언어 간 왕복 번역의 난이도는 성공률이나 반복 횟수 하나로 충분히 설명되지 않으며, 기능 실패, 구조적 안정화, 변환 비용을 분리한 모델 조건부 프로파일로 평가해야 한다.

그리고 이를 뒷받침할 가장 중요한 실험은, 그 프로파일이 단순 성공률보다 실제 번역 실패와 수정 비용을 더 잘 설명하거나 예측하는지 검증하는 것입니다. 이 결과가 확보되면, 함수형, 논리형 언어 분석과 GNN 기반 모델 자동 선택이 각각 독립적인 후속 연구로 자연스럽게 이어질 수 있습니다.
