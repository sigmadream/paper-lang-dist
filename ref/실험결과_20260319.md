# 결과 비교 분석 (OpenAI vs Ollama)

- 잔류 유사도(Residual similarity): 번역된 코드가 원본 코드의 변수명, 함수명, 텍스트 토큰 등을 얼마나 그대로 유지(잔류)하고 있는지를 0에서 1 단위 정규화 수치로 나타냅니다. 1에 가까울수록 원본 스크립트를 거의 '직역'하듯 텍스트를 그대로 유지했음을 뜻합니다.
    - Sørensen-Dice Coefficient (Sørensen-Dice 유사도): C++ 소스 코드를 토큰(Token) 단위로 분해한 뒤 두 집합 간의 교집합 크기를 바탕으로 유사도를 측정합니다. 자카드 유사도(Jaccard)와 비슷하지만 일치하는 요소에 가중치를 더 두어 코드 텍스트의 일치율을 계산합니다.

- 추상 구문 트리(AST) 구조적 일치(AST distance): AST 거리는 "원본 트리 구조에서 변환된 트리 구조를 만들기 위해 뼈대를 몇 개나 부수고 고쳤는가"를 측정한 값입니다. 수치가 클수록(거리가 멀수록) 로직의 구조 자체를 타겟 언어에 맞게 대대적으로 재배치(의역)했음을 뜻합니다. 반대로 수치가 작으면 원본의 뼈대를 그대로 유지했다는 의미입니다.
    - APTED (Algorithm for the Principal Tree Edit Distance): 두 개의 추상 구문 트리(AST) 간의 최소 편집 거리(Tree Edit Distance)를 구하는 알고리즘으로, 원본 트리에서 타겟 트리를 만들기 위해 노드를 삽입(Insert), 삭제(Delete), 변경(Rename)하는 데 드는 최소 비용을 수학적으로 계산해 구조적 훼손도를 도출합니다.
    - 단, AST 거리의 경우, 서로 다른 프로그래밍 언어 간의 트리를 비교할 때 언어별 파서의 어휘 차이 때문에 거리가 실제보다 훨씬 멀게 측정될 수 있다

## 언어 변환 쌍(Ordered Pair)별 결과 비교 분석

### C++ → C 변환 (`cpp->c`)

- OpenAI: 두 개의 문제 모두 성공(Success)하였으며, 2회의 반복(Iteration) 안에 고정점(Fixed Point) 수렴을 달성했습니다.

- Ollama: 단일 시도(IPOP_1436)에서 타겟 실행 중 시간 초과(Timeout)가 발생하여 실패했습니다. 

분석: C++에서 C로의 언어 간 변환에서는 OpenAI가 안정적인 성능을 보여주었으나, Ollama는 런타임 환경 또는 코드 생성 문제로 인해 무한루프나 교착상태(시간 초과)에 빠지는 취약점을 보였습니다.

### C++ → Java 변환 (`cpp->java`)

- OpenAI: 두 문제 모두 컴파일 오류(Compile Error) 또는 파싱 오류(Parse Error)가 발생하여 실패했습니다.

- Ollama: 2회의 반복(Iteration) 내에 성공(Success)적으로 고정점에 도달하였으며 의미론적 검증(Semantic pass)을 통과했습니다. 잔류 유사도(Residual similarity)는 약 87%로 나타났습니다.

분석: 객체지향 언어인 Java로의 변환에서는 정반대의 결과가 나타났습니다. OpenAI는 언어 구조적 차이를 극복하지 못하고 컴파일 에러를 발생시킨 반면, Ollama는 성공적으로 코드를 변환하고 Roundtrip 테스트까지 통과하는 성과를 보였습니다.

### C++ → Python 변환 (`cpp->python`)

- OpenAI: 두 문제 모두 컴파일/문법 오류로 인해 실패하였으며, 의미론적 검증 과정을 통과하지 못했습니다.

- Ollama: 3회의 반복(Iteration)을 거친 후 성공(Success)적으로 고정점에 도달하였고 의미론적 제약도 통과했습니다. 잔류 유사도는 약 81%를 기록했습니다.

분석: 동적 타이핑 언어인 Python으로의 언어 변환 역시 Java와 유사한 결과를 보였습니다. Ollama는 파이썬 문법 구조 안팎으로 안정적인 결과물을 생성했습니다. 반면 OpenAI 모델은 왕복(Roundtrip) 실행 단계에서 에러를 이겨내지 못했습니다.

## 코드 유사도 및 구조적 거리(AST) 분석

모델 및 대상 언어에 따라 생성된 코드의 일치도와 추상 구문 트리(AST) 구조적 일치도 양상에 차이가 발견되었습니다.

### 잔류 유사성(Residual Similarity) 및 MOSS 유사도

- OpenAI (C 원활): C++에서 C로 매끄럽게 변환한 결과물들의 잔류 유사도는 대략 `0.72 ~ 0.76` 범위를 보였습니다. MOSS 기준 원본 대비 유사도는 `0% ~ 30%` 수준에 그쳐, 코드는 상당히 재구성(포인터 체계 변환 등)되었음이 확인됩니다.

- Ollama (Java/Python 원활): C++에서 Java/Python으로 성공적으로 변환해낸 결과물들의 잔류 유사도는 Java에서 약 `0.87`, Python에서 약 `0.81`로 높게 나타났습니다. Ollama는 원본 코드의 변수명이나 전체적인 논리 흐름을 최대한 타겟 언어 구문에 맞춰 텍스트 그대로 유지하려는 성향이 엿보입니다.

### AST(Abstract Syntax Tree) 거리 분석

- OpenAI (C 변환): 성공한 C 코드들의 원본과의 AST 거리는 `18 ~ 41`로 측정되었습니다. C++ 특유의 추상화 요소(클래스 등)가 C로 번역되면서 구문 트리상 큰 폭의 재배치 구별을 보였습니다.

- Ollama (Java/Python 변환): 성공한 Java 변환 결과물의 AST 거리는 `12`에 불과했습니다. C++과 Java가 다수의 객체지향성 패러다임과 구조체계를 공유하므로, AST 구조 자체가 크게 왜곡되지 않고 변형에 성공했습니다. 반면 문법 구조의 이질감이 큰 Python으로의 변환에서는 AST 거리가 `33`으로, Java에 비해 더 큰 구조적 재조정이 발생했습니다.

## 종합 결론 및 시사점

1. 언어 특성에 따른 성능 분리: OpenAI는 C 언어와 같은 저수준, 절차적 언어로의 번역 및 구조 유지에 견고한 모습을 보입니다. 다만, Java나 Python 등 고수준 추상화가 강한 언어로 돌려 검증하는 경우 문법 및 컴파일 제약을 벗어나지 못했습니다. 그리고 Ollama의 경우 C 변환에서는 기초적인 런타임 제어(시간 초과 등)에 취약했으나, Java, Python과 같은 고도화된 객체/스크립트 언어로의 변환과 의미론적 정합성 유지에서는 OpenAI보다 매우 뛰어난 적응력을 발휘했습니다.

2. 수렴 양상: 성공적인 변환과 고정점 도달을 이뤄낸 경우, 두 모델 모두 2~3회 수준의 반복적인 수정 사이클(Change-count distance)을 통해 최종 완성형 코드를 도출했습니다. 이는 프레임워크 상클이 양측 모델에서 적절하게 재시도 기회를 활용하고 있다는 것을  방증합니다. 

본 두 모델의 장단점이 극명하게 갈리는 결과에 비추어 향후 실험 확장에서는 목적 언어(C vs Java/Python)에 따라 변환 LLM을 동적으로 라우팅하는 하이브리드 파이프라인 구성이 효과적일 수 있습니다.

## OpenAI 모델의 역설적 실패 사유

이번 실험 결과를 살펴보면, 앞선 언어들에서 전반적으로 더 우수하다고 평가받는 OpenAI(GPT 계열) 모델이 Java나 Python 같은 타겟 언어 변환 과정에서 오히려 더 잦은 실패를 겪는 흥미로운 현상을 관찰할 수 있었습니다. 

### 과도한 공학적 기술 적용

OpenAI 모델은 단순히 코드를 1:1로 직역하기보다는, 타겟 언어 고유의 디자인 패턴이나 관용적 표현(Idiom)을 적극적으로 반영하려는 경향이 뛰어납니다. 예를 들어, 변환된 코드를 보면 다분히 "Python스러운" 혹은 "Java스러운" 로직으로 구조 전체가 유려하게 재배치된 것을 확인할 수 있습니다. 

하지만 이러한 뛰어난 코드 리팩토링 징후가 이 실험의 엄격한 왕복 타당성 검증(Roundtrip: C++ → Target → C++) 프레임워크에서는 도리어 치명적인 오류로 작용했습니다. 코드가 원래의 C++ 뼈대와 너무 달라진 나머지, 역참조를 통해 다시 C++로 변환할 때 시스템이 대응 관계를 잃고 컴파일 에러(Compile/Parse Error)를 발생시키게 된 것입니다.

### 구문 트리(AST) 변경과 테스트 프레임워크의 한계

OpenAI 모델이 1차 타겟 언어 번역 자체는 성공적으로 수행했다(`target=success`)는 기록이 상당히 많습니다. 진짜 문제는 이를 원형인 C++로 다시 되돌리는 `roundtrip_cpp` 과정에서 집중적으로 발생했습니다.

반면 Ollama 모델은 복잡한 의미론적 리팩토링을 지양하고, 토큰 단위의 직역(Literal Translation)에 충실한 결과(잔류 유사도 0.81~0.87 유지)를 보여주었습니다. 이는 원본 코드의 변수명은 물론 구문 트리(AST)의 형상 자체를 충실히 보존해 주었으며, 그 덕분에 기계적인 복원 절차가 핵심인 왕복 테스트 프레임워크를 훨씬 안정적으로 통과하는 결정적 기반이 되었습니다.

### 통제된 환경에서의 라이브러리 환각(Hallucination) 약점

마지막으로 짚어볼 점은 언어 변환 과정에서 발현되는 환각 현상입니다. OpenAI 모델은 C++ 특유의 원시적인 포인터 제어나 메모리 락킹 로직을 타 언어에서 매끄럽게 모사하기 위해, 종종 외부 라이브러리를 임의로 `import`하거나 존재하지 않는 래퍼(Wrapper) 객체를 자체적으로 창조해내는 모습을 보입니다.

저희가 구성한 테스트 환경은 격리 환경이므로, 이러한 임의의 외부 패키지들이 준비되어 있지 않기 때문에, 이런 똑똑한 우회 시도가 도리어 즉각적인 파싱 코드나 컴파일의 실패로 직결되고 맙니다.


> "타겟 언어의 패러다임에 맞춰 코드를 완벽하게 최적화하려는" 고성능 AI의 압도적이고 유려한 추론 능력이, 원형 코드의 구조적 보존율을 깐깐하게 채점하는 닫힌 쌍방 번역(Roundtrip) 테스트 생태계 안에서는 오히려 오답(실패율 증가)으로 이어지는 일종의 '패널티'로 작용한 셈이라고 해석해 볼 수 있겠습니다.

## 보강자료

작성해주신 실험 결과와 분석 리포트는 통찰력이 매우 뛰어납니다. 특히 "고성능 모델(OpenAI)의 유려한 타겟 언어 최적화(Idiomatic Translation) 능력이, 뼈대 보존을 깐깐하게 따지는 왕복(Roundtrip) 검증 프레임워크에서는 오히려 패널티로 작용한다"는 '역설적 실패 사유'를 짚어낸 부분은 LLM 기반 코드 생성 및 번역 평가의 핵심적인 딜레마를 정확히 관통하고 있습니다. 

이러한 훌륭한 분석을 바탕으로, 현재의 실험 프레임워크를 보완하고 향후 실용적이고 강건한 코드 변환 파이프라인으로 고도화하기 위해 적용해 볼 수 있는 5가지 개선 및 확장 방안을 추천해 드립니다.

### 1. 평가 프레임워크 다각화: '구조' 중심에서 '기능/의미' 검증 추가

현재의 왕복 검증(C++ $\rightarrow$ Target $\rightarrow$ C++)은 코드의 기계적인 가역성(Reversibility)을 평가하는 데는 훌륭하지만, OpenAI가 성공적으로 수행한 고품질의 '의역(리팩토링)' 코드를 오답으로 억울하게 처리할 위험이 있습니다.

실행 기반 단위 테스트(Execution-based Unit Testing) 도입: 왕복 테스트에 앞서, 1차로 변환된 타겟 언어 코드 자체의 입출력(I/O)을 검증하는 단계를 추가해야 합니다. 원본 C++과 동일한 입력에 대해 동일한 출력을 반환한다면(기능적 동치성), AST 구조가 크게 바뀌었더라도 '의미론적 성공(Semantic Success)'으로 정당하게 평가받아야 합니다.

- 평가 트랙의 이원화:
    - `직역(Literal) 트랙`: 원본의 AST 구조 유지 및 왕복 성공률 (현재 Ollama가 우위인 지표)
    - `의역(Idiomatic) 트랙`: 타겟 언어 내 단위 테스트 통과율(Pass@k) 및 코드 복잡도 감소율 (OpenAI의 진정한 코딩 성능을 볼 수 있는 지표)


### 2. 향상된 의미론적 유사도 메트릭 도입

AST 거리는 분석에서 언급하셨듯 서로 다른 언어의 파서(Parser) 차이로 인해 노이즈가 발생하기 쉽습니다. 표면적인 뼈대가 아닌 로직의 본질적인 유사도를 측정할 추가 지표가 필요합니다.

데이터 흐름 유사도 (Data-Flow Graph, DFG): 단순 구문(Syntax)이 아니라 변수의 할당과 참조 흐름(Semantics)을 추적합니다. (예: C++의 `for`문이 Python의 `List Comprehension`으로 바뀌어도 데이터 흐름은 동일함)

코드 임베딩 기반 유사도 (CodeBERT / GraphCodeBERT): AI 모델을 활용해 두 코드의 '의미적 벡터 공간' 내 거리를 측정하면, 언어별 문법 차이를 넘어 기능적으로 얼마나 유사한지 수치화할 수 있습니다.

### 3. 프롬프트 엔지니어링을 통한 '모델별 약점 제어 (Sandboxing)'

실험에서 드러난 각 모델의 치명적 약점은 시스템 프롬프트(System Prompt) 상의 명시적 제약(Constraints)을 통해 상당 부분 억제할 수 있습니다.

- OpenAI (환각 통제 및 번역 스타일 강제): 
    - 환경 통제: `"이 환경은 외부 네트워크가 차단된 격리 환경입니다. 외부 라이브러리(Third-party packages) 임포트를 절대 금지하며, 오직 타겟 언어의 표준 내장 라이브러리만 사용하시오."`
    - 스타일 강제: 왕복 테스트 통과가 최우선 목적일 경우, `"타겟 언어의 관용적 표현으로 리팩토링하지 말고, 원본 C++의 변수명과 AST 구조를 최대한 1:1로 유지하여 직역(Literal Translation)하시오."`라고 명시하여 과도한 똑똑함을 제어합니다.

- Ollama (C 언어 런타임 안정성 확보): C언어 변환 시 무한 루프나 시간 초과(Timeout)에 빠지는 것을 막기 위해 방어적 프로그래밍을 유도합니다.
    - 지시어: `"포인터 연산 시 엄격한 경계 검사를 수행하고, 무한 루프에 빠지지 않도록 while/for 문의 명확한 종료 조건을 반드시 포함하시오."`

### 4. 에러 피드백을 활용한 '자가 수정(Self-Correction) 루프' 고도화

현재 두 모델 모두 2~3회의 반복(Iteration) 내에 고정점에 도달하는 훌륭한 시스템을 갖추고 계십니다. 이 루프의 효율을 극대화하려면 피드백의 질을 높여야 합니다.

- 컴파일러/인터프리터 에러 로그 직접 주입: 타겟 언어 실행 또는 왕복 컴파일에서 실패했을 때, 단순히 "다시 생성하라"고 지시하는 대신 실제 발생한 에러 로그(Traceback, Compile Error)를 다음 프롬프트에 그대로 포함시킵니다.

    - *"네가 작성한 코드에서 `ImportError: module not found` 에러가 발생했다. 해당 외부 패키지 없이 순수 기본 문법만으로 로직을 우회하여 재작성하라"*고 구체적으로 피드백하면, 환각 현상 등을 모델 스스로 즉각 교정할 수 있습니다.

### 5. 제안하신 '하이브리드 파이프라인'의 시스템적 구체화 (라우팅 & 폴백)

결론부에서 제안하신 "목적 언어에 따른 동적 라우팅" 아이디어는 실제 서비스 적용 시 가장 강력하고 실무적인 아키텍처가 될 수 있습니다.

- 언어 및 목적 기반 동적 라우터 (Task-based Router):
    - `Target = C 언어` (저수준 메모리 제어 필요) $\rightarrow$ OpenAI 전담
    - `Target = Java/Python` (안정적인 1:1 구조 유지 필요) $\rightarrow$ Ollama 전담

- 폴백(Fallback) 기반 캐스케이딩(Cascading) 모델 구축: 무조건 분기하는 것을 넘어 상호 보완적으로 활용합니다.
    
    1.  먼저 OpenAI에게 변환을 맡겨 '고품질의 리팩토링된 코드' 생성을 시도합니다.
    2.  만약 라이브러리 환각이나 컴파일 에러로 인해 1~2회 시도 내에 실패할 경우, 프레임워크가 이를 즉각 감지합니다.
    3.  안전하고 구조 보존력이 뛰어난 Ollama로 Fallback(대체 호출)하여 '직역본'을 생성하도록 우회시킴으로써, 전체 파이프라인의 작업 성공률(Success Rate)과 신뢰성을 극대화할 수 있습니다.

### 6. 요약하자면

도출하신 실험 분석은 완벽합니다. 다음 단계의 연구에서는 모델의 높은 지능으로 인해 억울하게 오답 처리되는 케이스를 구제할 수 있도록 ① 단위 테스트 중심의 '기능적(Semantic) 검증'을 추가하시고, ② 명시적 제약 조건(Constraints) 프롬프트를 도입하며, ③ 제안하신 하이브리드 라우팅/폴백 모델을 실제 시스템으로 구현해 보는 방향으로 나아가시길 적극 추천해 드립니다.
