# 제안서 학술 중심 종합 정리

## 1. 전체 총평

첨부 문서의 제안 1~4는 공통적으로 현재 연구를 LLM 왕복 번역과 고정점 개념을 결합하여 프로그래밍 언어 간 차이를 정량화하려는 파일럿 연구로 해석합니다. 현재 방법은 언어 A의 프로그램을 언어 B로 번역한 뒤 다시 A로 되돌리고, 의미 보존 여부·구조 변화·고정점 도달 횟수를 측정한다는 점에서 독창적인 출발점을 갖습니다. 

향후 연구를 위해서 문헌 검토를 진행해본 결과, 가장 중요한 결론은 다음과 같습니다.

> 언어와 문제 수를 단순히 늘리는 것이 아니라, 지금 측정되는 값이 정말 "프로그래밍 언어의 거리"인지 먼저 이론적·통계적으로 검증하는 것입니다.

현재 관측되는 고정점 반복 횟수와 의미 보존률에는 언어쌍뿐 아니라 모델, 프롬프트, 샘플링 정책, 문제 유형, 테스트 강도 등이 함께 반영됩니다. 따라서 이를 곧바로 언어 자체의 내재적 거리라고 부르기보다는 우선 "모델 조건부 왕복 변환 발산도"로 정의한 뒤, 여러 모델과 과제에서도 안정적으로 유지되는 성분을 언어 효과로 추정하는 방향이 가장 타당합니다.

## 2. 현재 연구의 학술적 기여

현재 연구의 기여는 세 가지로 정리할 수 있습니다.

### 2.1 왕복 번역을 언어 비교 문제로 확장

기존의 Round-Trip Correctness 계열은 코드에서 설명을 생성하고 다시 코드를 복원하거나, 번역 결과를 역변환해 원래 의미가 유지되는지를 평가하는 방식입니다. 현재 연구는 이를 서로 다른 프로그래밍 언어 사이의 코드→코드 왕복 변환으로 확장하고, 왕복 과정에서 발생하는 손실을 언어쌍의 특성과 연결합니다.

### 2.2 단발성 성공률이 아니라 반복 동역학을 관찰

단순히 한 번 번역한 코드가 테스트를 통과하는지 보는 데서 그치지 않고, 번역을 반복했을 때 코드가 안정되는지와 안정되기까지 몇 번의 반복이 필요한지를 분석합니다. 즉, 번역 결과를 정적인 산출물이 아니라 반복 변환 과정에서 움직이는 상태로 본다는 점이 특징입니다.

### 2.3 구조 보존과 의미 보존이 서로 다른 축임을 관찰

특히 중요한 결과는 Qwen 계열의 C++ ↔ Python 왕복 변환에서 실행 테스트는 통과했지만 MOSS 유사도는 0%로 나타난 사례입니다. 이는 코드의 표면 구조가 거의 전면적으로 바뀌어도 기능적 의미는 보존될 수 있음을 보여줍니다. 따라서 현재 연구는 의도하지 않았더라도 구조적 거리와 의미적 거리를 분리해야 한다는 근거를 제공한 셈입니다. 

## 3. 가장 중요한 학술적 쟁점

| 쟁점         | 현재 방법의 문제                                | 권장되는 해결 방향                         |
| ---------- | ---------------------------------------- | ---------------------------------- |
| 구성 타당도     | 관측값에 언어·모델·과제·프롬프트 효과가 혼합됨               | 요인 설계와 혼합효과 모형으로 언어쌍 효과 분리         |
| 실패와 수렴의 혼동 | 첫 왕복에서 의미가 파괴되면 반복 횟수가 오히려 짧아질 수 있음      | 의미 실패를 별도 흡수 상태로 처리                |
| 고정점의 정의    | LLM 변환은 확률적이므로 정확한 문자열 고정점이 불안정함         | 의미 등가류에 대한 확률적 고정점 정의              |
| MOSS의 해석   | 토큰 지문 유사도는 의미·데이터 흐름을 직접 측정하지 않음         | AST·데이터 흐름·임베딩·실행 지표와 결합           |
| 거리 공리      | 대칭성과 삼각부등식이 성립한다는 보장이 없음                 | 우선 방향성 발산도라고 명명                    |
| 외적 타당도     | BOJ 5문제로는 언어의 다양한 특성을 대표하기 어려움           | 통제된 미세 과제, 다언어 벤치마크, 실제 코드로 단계적 확대 |
| 재현성        | 모델 버전, 온도, 프롬프트, 샘플링 횟수에 따라 결과가 달라질 수 있음 | 모델 스냅샷과 모든 생성 설정을 기록하고 반복 표본 사용    |

### 3.1 언어 거리와 모델 능력이 섞여 있습니다

동일한 언어쌍에서도 모델에 따라 의미 보존률과 반복 횟수가 크게 달라진다면, 관측된 값은 언어 자체의 속성만으로 설명할 수 없습니다. 제안서에서는 이를 다음과 같은 연구 설계상의 분해로 표현합니다.

$$
D_{\mathrm{obs}}
=
D_{\mathrm{language}}
+
D_{\mathrm{model}}
+
D_{\mathrm{task}}
+
D_{\mathrm{prompt}}
+
D_{\mathrm{interaction}}
+
\epsilon
$$

이 식은 실제 거리의 완성된 수식이라기보다, 후속 연구에서 반드시 분리해야 할 효과들을 나타냅니다. 

따라서 후속 실험은 최소한 다음 요인을 교차해야 합니다.

* 언어쌍
* 모델 계열과 모델 크기
* 문제 또는 프로그램
* 프롬프트 정책
* 온도·시드·샘플링 반복
* 왕복 방향

통계적으로는 프로그램을 임의효과로 두는 혼합효과 모형이나 베이지안 계층 모형을 사용하여, 언어쌍 효과와 모델×언어쌍 상호작용을 분리하는 것이 적절합니다.

### 3.2 빠른 종료가 가까운 거리를 의미하지 않습니다

현재 지표에서 가장 심각한 역전 가능성은 의미가 일찍 파괴된 프로그램이 더 빨리 고정되는 것처럼 보이는 현상입니다. 예를 들어 첫 왕복에서 잘못된 코드가 생성되고 이후 계속 비슷한 잘못된 코드만 생성된다면, 반복 횟수는 짧지만 좋은 번역이나 가까운 언어쌍이라고 볼 수 없습니다.

따라서 다음 두 사건을 구분해야 합니다.

1. 의미를 보존한 상태에서 의미적 고정점에 도달함
2. 의미를 잃은 실패 상태에 도달함

제안서가 제안한 의미 생존 보정은 이 문제를 직접 해결합니다. 

통계적으로는 이를 단순 평균 반복 횟수보다 경쟁위험 모형 또는 다중 상태 생존 모형으로 다루는 것이 좋습니다. 하나의 종착 상태는 의미적 수렴이고, 다른 종착 상태는 컴파일 실패·테스트 실패·시간 초과 등의 의미 손실입니다.

### 3.3 지금의 고정점은 형식 의미론의 고정점과 구분해야 합니다

프로그램 의미론에서의 최소 고정점은 완비 격자, 단조성, 연속성 등의 수학적 조건 아래 정의됩니다. 그러나 LLM 기반 번역은 일반적으로 결정론적 함수도 아니고, 단조 연산자나 축약사상이라는 보장도 없습니다.

따라서 현재 연구에서 관찰되는 것은 엄밀히 말해 다음에 가깝습니다.

* 경험적 반복 안정화
* 문자열 또는 정규화된 코드의 반복 재현
* 의미 등가류에 대한 확률적 재진입
* 제한된 반복 횟수 안에서의 흡수 또는 순환

제안 3에서 추상 해석의 고정점과 LLM 왕복 수렴이 사실상 동일한 원리를 공유한다고 강하게 연결한 부분은 학술적으로 과도합니다. 두 현상은 비유적·개념적으로 연결할 수 있지만, 동일하다고 주장하려면 왕복 연산자의 상태 공간, 순서 구조, 단조성, 수렴 조건을 별도로 증명해야 합니다.

## 4. 권장되는 이론적 재정의

제안서에서 가장 학술적 가치가 높은 개념은 의미 생존 보정 확률적 고정점 거리입니다.

모델 \(m\), 프롬프트 정책 \(\pi\)에 대해 언어 A에서 B로의 번역을 \(T^{m,\pi}_{A\to B}\)라고 하면, 한 번의 왕복 연산은 다음과 같이 표현할 수 있습니다.

$$
R^{m,\pi}_{A,B}
=
T^{m,\pi}_{B\to A}
\circ
T^{m,\pi}_{A\to B}
$$

그러나 \(R\)은 고정된 결정론적 함수라기보다 출력 분포를 만드는 확률적 전이 연산자로 보는 편이 적절합니다.

문자열의 정확한 동일성

$$
x_{t+1}=x_t
$$

대신 다음과 같이 의미 등가 관계를 도입합니다.

$$
x_{t+1}\approx_{\mathrm{sem}}x_t
$$

여기서 \(\approx_{\mathrm{sem}}\)은 다음 중 하나 또는 복수의 조건으로 정의할 수 있습니다.

* 확장된 테스트 집합에서 출력 일치
* 입력별 실행 추적 일치
* 상태 변화 또는 데이터 흐름의 허용 범위 내 일치
* 특정 언어쌍에서 가능한 정형 동치 검증
* 속성 기반 테스트를 통한 의미 관계 보존

제안서에서는 이를 \(\epsilon\)-의미 고정점 등가류라고 설명합니다. 

이를 종합하면 다음과 같은 방향성 발산도를 정의할 수 있습니다.

$$
D_{A\Rightarrow B}
=
\lambda_f P(F_K=1)
+
\lambda_t
E\left[
\frac{\min(\tau_\epsilon,K)}{K}
\mid F_K=0
\right]
+
\lambda_s E[d_{\mathrm{struct}}\mid F_K=0]
+
\lambda_u U
$$

* \(F_K\): \(K\)회 안에 의미가 소실되었는지
* \(\tau_\epsilon\): 의미적 \(\epsilon\)-고정점에 최초 도달한 시점
* \(d_{\mathrm{struct}}\): 구조 변화량
* \(U\): 모델·시드·프롬프트 변화에 대한 불안정성
* \(\lambda\): 각 구성 요소의 가중치

중요한 점은 이 값을 처음부터 수학적 metric이라고 부르지 않는 것입니다. 대칭성이나 삼각부등식이 검증되기 전에는 방향성 발산도(directed divergence) 또는 모델 조건부 변환 비용이 더 정확한 명칭입니다.

## 5. MOSS의 학술적 위치

MOSS를 완전히 폐기할 필요는 없지만, 주된 언어 거리로 사용하는 것은 피하는 편이 좋습니다.

MOSS가 원본 언어 코드와 왕복 후 동일 언어 코드를 비교하므로 서로 다른 언어의 파일을 직접 비교하는 것은 아닙니다. 그럼에도 MOSS 점수는 근본적으로 다음에 민감합니다.

* 토큰의 지역적 중첩
* 문장 배열
* 구문적 재작성
* 식별자와 표면 구조의 변화

따라서 MOSS 0%는 "의미가 완전히 달라졌다"는 뜻이 아니라 왕복 과정에서 원래 토큰 골격이 거의 남지 않았다는 뜻에 가깝습니다. 실행 결과가 100% 보존된 사례는 MOSS의 실패라기보다는, MOSS와 실행 테스트가 애초에 서로 다른 구성개념을 측정한다는 사실을 보여줍니다.

후속 연구에서는 다음과 같은 다중 관점 측정이 적절합니다.

| 관점    | 후보 지표                         | 측정 대상          |
| ----- | ----------------------------- | -------------- |
| 어휘적   | MOSS, Winnowing, 토큰 편집 거리     | 표면 재작성 정도      |
| 구문적   | AST 편집 거리, TSED               | 문법·제어구조 변화     |
| 의존 구조 | CodeBLEU의 데이터 흐름, PDG/DFG     | 계산 의존 관계       |
| 표현 기반 | CodeBERTScore, 코드 임베딩         | 학습된 의미 표현의 근접성 |
| 동적 의미 | 테스트 통과, 실행 trace, 속성 기반 테스트   | 기능적 의미         |
| 정형 의미 | translation validation, 동치 검사 | 엄격한 의미 보존      |

제안서도 MOSS를 하나의 어휘적 관점으로 낮추고, AST·데이터 흐름·임베딩·실행을 병렬적으로 비교하는 방향을 권고합니다. 

특히 다음과 같은 통제된 반례 집합을 먼저 만드는 것이 중요합니다.

* 실행은 같지만 구조가 크게 다른 코드
* 구조는 비슷하지만 경계 조건에 버그가 있는 코드
* 변수명만 변경된 코드
* 반복문과 재귀가 상호 변환된 코드
* 리스트 내포와 명시적 반복문이 상호 변환된 코드
* 정렬·해시·트리 등 자료구조만 바뀐 코드

이 집합을 이용하면 각 지표가 실제로 무엇을 측정하는지 보정할 수 있습니다.

## 6. 가장 권장되는 실험 설계

### 6.1 데이터를 세 층으로 구성

첫 번째 층: 통제된 언어 기능 과제

한 번에 하나의 언어 특성만 변화시키는 작은 프로그램을 사용합니다.

* 정적 타입과 동적 타입
* 포인터와 참조
* 예외와 결과 타입
* 상속과 합성
* 클로저와 고차 함수
* 제너레이터와 지연 평가
* 가변 상태와 불변 상태
* 스레드·액터·비동기 처리

이 데이터는 "어떤 언어 특성이 거리를 증가시키는가"를 설명하는 데 적합합니다.

두 번째 층: 다언어 벤치마크

MultiPL-E, XCodeEval, CodeScope, CRUXEVAL-X 등과 같이 동일하거나 유사한 문제를 여러 언어에서 실행할 수 있는 자료를 이용합니다. 현재 다섯 BOJ 문제만으로는 타입 시스템, 메모리, 객체 모델, 예외, 동시성 등의 차이를 포괄하기 어렵다는 한계가 제안서에 명시되어 있습니다. 

세 번째 층: 실제 시스템 코드

OSS 함수나 모듈을 대상으로 실험하여 실제 마이그레이션·리팩터링 상황에서도 지표가 유효한지 검증합니다. 알고리즘 문제에서 얻은 거리가 실무 코드에서도 유지되는지는 별도의 외적 타당도 문제입니다.

### 6.2 현실적인 최소 실험 규모

제안서가 제시한 현실적 최소선은 다음과 같습니다.

* 8~12개 프로그래밍 언어
* 3~5개 모델 계열
* 최소 수백 개 프로그램
* 언어쌍·프로그램·조건별 반복 샘플
* 양방향 왕복 실험
* 다수의 시드 또는 독립 호출

정확한 표본 수는 소규모 파일럿에서 분산을 추정한 뒤, 검정력 분석이나 목표 신뢰구간 폭을 기준으로 정하는 것이 바람직합니다. 

### 6.3 보고해야 할 통계량

평균 반복 횟수 하나만 보고해서는 안 됩니다.

* 단계별 의미 생존율과 95% 신뢰구간
* 의미 고정점 도달시간 분포
* 의미 실패까지의 시간
* 모델 간 언어쌍 순위 상관
* 언어쌍 효과의 분산 비율
* 모델×언어쌍 상호작용
* 과제 유형×언어쌍 상호작용
* 부트스트랩 신뢰구간
* 방향 비대칭 지수
* 순환·진동·비수렴 비율

실패 사례를 제외하고 성공 사례의 평균 반복 횟수만 계산하면 생존자 편향이 발생하므로, 실패 자체를 핵심 관측값으로 포함해야 합니다.

### 6.4 재현성 기록

각 실험에는 최소한 다음 정보를 남겨야 합니다.

* 정확한 모델 식별자 또는 스냅샷
* 호출 날짜
* 시스템·사용자 프롬프트
* 온도, top-p, 최대 토큰
* 시드 또는 반복 횟수
* 컴파일러와 런타임 버전
* timeout과 메모리 제한
* 코드 정규화 절차
* 고정점 판정 규칙
* 테스트 케이스와 숨은 테스트의 구성

현재 자료만으로는 일부 생성·판정 설정을 확인하기 어렵다는 점도 제안서에서 재현성 한계로 지적됩니다.

## 7. 가장 강한 후속 논문 구성

### 제1논문: 의미 생존 보정 확률적 고정점 거리

가장 먼저 수행할 연구입니다.

핵심 질문

> 의미 보존 실패를 분리하고 LLM의 확률성을 반영한 고정점 지표가, 단순 반복 횟수보다 언어쌍의 안정적인 차이를 더 잘 포착하는가?

주요 기여

* 빠른 실패를 가까운 거리로 오인하는 문제 해결
* 의미적 고정점과 실패 상태의 분리
* 문자열 동일성 대신 의미 등가류 사용
* 거리보다 방향성 발산도라는 정확한 개념 제시

### 제2논문: 다중 관점 프로그래밍 언어 거리

핵심 질문

> 실행, AST, 데이터 흐름, 임베딩, 토큰 구조를 결합한 지표가 MOSS 단독보다 인간 판단과 모델 간 재현성에 더 잘 부합하는가?

주요 기여

* 구조와 의미의 명시적 분리
* 지표별 민감도 보정
* 통제된 반례 데이터셋 제공
* 복합 거리 또는 잠재요인 모델 제시

### 제3논문: 다언어·다모델 거리 지도

핵심 질문

> 모델과 과제가 바뀌어도 유지되는 언어쌍 효과가 존재하는가?

주요 기여

* 전 언어쌍 방향성 행렬
* 모델×언어×과제 효과 분해
* 언어쌍 순위 안정성 검증
* 언어 기능별 거리 원인 분석

다만 이 결과를 곧바로 "프로그래밍 언어 계통수"라고 부르는 것은 조심해야 합니다. 계통수는 역사적 계승 관계를 암시하지만, LLM 왕복 결과는 학습 데이터 분포와 모델 표현을 포함한 유사도입니다. 초기에는 다음과 같은 명칭이 더 적절합니다.

* 프로그래밍 언어 변환 지형도
* 모델 조건부 언어 유사도 지도
* 프로그래밍 언어의 방향성 변환 기하
* LLM 매개 언어 관계망

세 프로젝트는 각각 거리의 정의, 거리의 관측 방법, 거리의 일반화 가능성을 담당하는 순차적 연구 프로그램으로 정리할 수 있습니다.

## 8. 학술 문헌의 우선순위

제안서의 문헌들을 실제 연구 진행 순서에 맞추면 다음과 같습니다.

1. Round-Trip Correctness
   왕복 평가를 의미 보존과 연결하는 직접적인 이론적 출발점입니다.

2. TransCoder와 다언어 코드 번역 연구
   비지도 또는 LLM 기반 언어 간 번역의 성능과 실패 유형을 이해하는 데 필요합니다.

3. MultiPL-E·XCodeEval·CRUXEVAL-X 계열
   소규모 BOJ 실험을 다언어·대규모 실행 벤치마크로 확장하는 기반입니다.

4. HumanEval·EvalPlus 계열
   테스트 통과를 의미 보존 기준으로 사용할 때 테스트 강도가 얼마나 중요한지를 다룹니다.

5. Winnowing·TSED·CodeBLEU·GraphCodeBERT
   토큰, AST, 데이터 흐름, 표현 기반 유사도의 차이를 설계하는 데 필요합니다.

6. CompCert·Alive2와 translation validation
   "의미 보존"의 가장 엄격한 기준점을 이해하고 일부 언어쌍에서 정형 검증을 도입하는 근거입니다.

7. Csmith·Equivalence Modulo Inputs·Metamorphic Testing
   테스트 오라클이 불충분하거나 학습 데이터 오염이 의심되는 상황에서 새로운 프로그램과 검증 관계를 만드는 데 활용할 수 있습니다.

제안서에서도 RTC → TransCoder → 다언어 벤치마크 → EvalPlus → AST·데이터 흐름 지표 → CompCert·Alive2 → Csmith·EMI 순의 독서를 권장합니다.

## 9. 제안 1~4의 상대적 평가

| 제안       | 학술적 평가                                                                | 활용 방식                        |
| -------- | --------------------------------------------------------------------- | ---------------------------- |
| 제안 1 | 관련 분야와 응용 범위를 폭넓게 제시하지만 핵심 가설과 우선순위가 다소 약함                            | 관련 연구 장과 장기 아이디어 목록으로 활용     |
| 제안 2 | 구성 타당도, 실패 편향, 확률적 고정점, 다중뷰 측정, 통계 설계까지 가장 체계적임                       | 후속 논문의 주된 연구계획서로 채택          |
| 제안 3 | 디컴파일·HDL·자가 수리 등 응용은 창의적이지만, 추상 해석과 LLM 수렴을 동일시하고 학술적 의미를 과장하는 표현이 많음 | 장기 응용 아이디어만 선별하여 활용          |
| 제안 4 | 간결하면서도 모델 교란, MOSS 한계, 다언어 확대, 통계적 엄밀성을 정확히 짚음                        | 제안 2의 체크리스트와 관련 연구 보강 자료로 결합 |

제안 1은 이론·실험·응용 논문이라는 세 갈래의 연구 프로그램을 구성한다는 점에서 유용합니다. 

제안 2는 "무엇을 거리라고 부를 수 있는가"를 먼저 재정의해야 한다는 판단과 세 가지 최우선 연구를 명확하게 제시하므로 학술적으로 가장 강합니다. 

제안 3은 응용 아이디어가 풍부하지만 "수학적으로 강한 지지", "완벽히 동일한 원리", "세계 최초", "기념비적" 같은 서술은 실제 증명과 체계적 문헌조사 없이는 논문에서 사용하기 어렵습니다. 또한 MOSS를 언어 구조의 본질을 정확히 포착하는 지표로 높게 평가한 부분은, 동일 문서의 다른 제안들이 지적한 MOSS의 어휘적 한계와 충돌합니다. 

제안 4는 현재 약점과 대응 방향을 가장 압축적으로 연결합니다. 특히 소규모 코퍼스, C++ 단일 기준, 모델 교란, MOSS 한계, 비대칭성, 통계적 검정 부족을 각각 후속 실험 항목과 대응시킨 부분이 유용합니다.

## 10. 응용 연구의 우선순위

제안서에는 교육, 코드 검색, 표절 탐지, 레거시 현대화, 자동 수리, 컴파일러 검증, 디컴파일, HDL 변환, 모델 라우팅 등의 응용이 제시되어 있습니다. 그러나 학술적으로는 다음 순서를 권장합니다.

### 1순위: 레거시 코드 현대화와 자동 이식

왕복 후 의미 생존률을 함수별 마이그레이션 위험 점수로 사용할 수 있습니다. 현재 연구의 방법을 가장 자연스럽게 실무로 확장하는 응용입니다.

### 2순위: 모델·번역 경로 라우팅

언어쌍, 코드 유형, 요구사항에 따라 모델이나 중간 표현 경로를 선택합니다. 다만 비용 절감 효과는 별도의 시스템 실험으로 검증해야 하며, 일반 LLM 라우팅 연구의 수치를 코드 번역에 그대로 적용해서는 안 됩니다.

### 3순위: 교차 언어 코드 클론 탐지

여러 언어의 코드를 공통 표현이나 공통 언어로 정규화한 뒤 의미적 유사성을 비교하는 방식입니다. MOSS 0%·실행 100% 사례를 가장 독창적으로 활용할 수 있습니다.

### 4순위: 자동 프로그램 수리

버그 코드를 다른 언어나 자연어 명세로 변환했다가 복원하면서 테스트 피드백을 결합합니다. 이 경우 반복 횟수는 언어 거리보다 결함 수정 난이도에 가까운 지표가 됩니다.

디컴파일, HDL, 하드웨어 설계 응용은 흥미롭지만 소프트웨어와 하드웨어 사이의 의미 동치 기준, 타이밍 의미론, 최적화 조건 등 별도의 어려운 문제가 발생하므로 장기 연구로 두는 편이 적절합니다. 제안서도 응용 가능성을 폭넓게 제시하지만, 중심 연구는 여전히 거리의 정의와 검증에 두고 있습니다.

## 11. 최종적으로 권장되는 논문 프레이밍

### 권장 연구 질문

> LLM을 매개로 한 프로그래밍 언어 간 왕복 변환에서 관측되는 의미 손실과 수렴 과정 중, 언어쌍에 기인하는 성분을 모델·과제·프롬프트 효과로부터 분리하여 재현 가능한 방향성 발산도로 정의할 수 있는가?

이 질문은 현재 연구의 아이디어를 유지하면서도 다음 약점을 모두 연구 문제로 전환합니다.

* 모델마다 결과가 크게 다른 현상
* 빠른 실패가 짧은 수렴처럼 보이는 현상
* MOSS와 실행 의미가 불일치하는 현상
* 소규모 과제와 단일 기준 언어의 한계

### 권장 핵심 주장

기존 주장:

> LLM 왕복 번역에서 고정점까지의 반복 횟수로 프로그래밍 언어 간 거리를 측정할 수 있다.

개선된 주장:

> 프로그래밍 언어 간 LLM 왕복 변환은 모델과 과제에 의존하는 확률적 동역학이며, 언어쌍의 차이는 단순 반복 횟수가 아니라 의미 생존 확률, 의미적 고정 등가류 도달시간, 구조·데이터 흐름 변화, 모델 간 안정성을 함께 고려한 방향성 발산도로 추정해야 한다.

이 재정의가 제안서 전체에서 가장 학술적으로 설득력 있는 결론입니다. 

### 권장 제목

국문

> LLM 왕복 번역에서 의미 생존과 확률적 고정점을 이용한 프로그래밍 언어 간 방향성 발산도

영문

> Model-Conditioned Stochastic Semantic Divergence between Programming Languages via Round-Trip Translation

## 12. 종합 판단

네 제안을 통합할 때 가장 적절한 선택은 다음과 같습니다.

* 제안 2를 연구의 주된 뼈대로 사용
* 제안 4를 비판적 체크리스트와 문헌 보강 자료로 결합
* 제안 1을 관련 연구와 장기 연구 프로그램 정리에 활용
* 제안 3은 과장된 이론적 표현을 제거하고 응용 아이디어만 선별

현재 논문의 약점은 단순히 표본이 작다는 데 있지 않습니다. 오히려 더 근본적인 문제는 측정된 값이 언어의 차이인지, 모델의 번역 정책인지, 실패로 인한 가짜 수렴인지 아직 분리되지 않았다는 것입니다. 따라서 가장 강한 후속 논문은 언어 수를 늘리는 논문이 아니라, 먼저 거리 개념을 의미 생존과 확률적 고정점에 기반하여 재정의하고, 그 지표가 여러 모델과 데이터에서도 안정적인지를 검증하는 논문입니다.

또한 제안서 내부에서 문헌의 존재와 서지사항을 확인했다고 밝히고 있지만, 실제 논문 작성 단계에서는 논문명·연도·학회·수치·모델 표기를 반드시 1차 출처에서 다시 대조해야 합니다. 특히 프리프린트의 정량 주장, 특정 라우팅 연구의 비용 절감 수치, 모델 버전 관련 서술은 그대로 일반화하지 않는 것이 안전합니다.
