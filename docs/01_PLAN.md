## 1. 목적과 범위

C++·Haskell·Prolog를 각각 출발 언어로 삼아 왕복 번역(Round-Trip Translation, RTT)을 반복하고, 기능 성공률 $P_{sf}$, 코드 유사도 $Sym$, 수렴 거리 $d_n$을 측정한다. 명령형·함수형·논리형 표현을 사용하는 경로에서 기능 보존과 표현 안정화가 어떻게 달라지는지 비교한다. 서로 다른 패러다임의 거리가 반드시 길다는 결론을 전제하지 않는다.

사용자 요구와 이 계획의 구체화는 다음과 같다.

| 항목 | 요구사항 또는 설계안 |
| --- | --- |
| 출발 언어 | C++, Haskell, Prolog를 모두 포함 |
| 비교 경로 | 세 언어 사이의 방향을 구분한 6개 왕복 경로 |
| 샘플 | 세 언어로 모두 구현·검증 가능한 공통 문제 10~20개; 목표 15개 |
| 주 지표 | $P_{sf}$, $Sym$, $d_n$을 별도로 보고 |
| 수렴 판정 | 인접 복원 코드의 유사도가 임계값 이상이면 근사 고정점 도달로 판정 |
| 임계값 | 초안 0.85; 검증 후 본 실행 전에 확정·동결 |
| 거리 단위 | 사용자 확정: FPS 크기, 즉 출발 코드를 포함한 서로 다른 상태 수 |
| 거리 상한 | FPS 크기가 10을 초과하면 추가 번역 중지; 왕복 10회 제한과 구분 |
| 모델 확장 | LM Studio 유지, 다른 모델·제공자로 설정만 바꾸어 실행할 수 있도록 라이브러리 개선 |

기존 해시 일치 기반 실험과 새 유사도 임계값 기반 실험은 판정 규칙이 다르다. 기존 결과를 새 방식의 결과로 바꾸어 표시하거나 합산하지 않는다. 이번 문서 작업은 라이브러리 구현이나 모델 호출을 실행했다는 뜻이 아니다.

## 2. 언어 경로와 관측 단위

출발 언어를 A, 중간 언어를 B로 두며 A와 B는 서로 다르다.

| 출발 A | 중간 B | 왕복 경로 |
| --- | --- | --- |
| C++ | Haskell | C++ → Haskell → C++ |
| C++ | Prolog | C++ → Prolog → C++ |
| Haskell | C++ | Haskell → C++ → Haskell |
| Haskell | Prolog | Haskell → Prolog → Haskell |
| Prolog | C++ | Prolog → C++ → Prolog |
| Prolog | Haskell | Prolog → Haskell → Prolog |

기본 관측 단위는 `문제 × 출발 언어 × 중간 언어 × 모델 × 전체 실행 반복`이다. 같은 문제·출발 언어의 두 경로는 같은 기준 코드를 사용한다. 반대 방향의 두 경로는 서로 다른 관측으로 유지한다. C·Python·Java·Scala를 중간 언어로 추가하는 실험은 이번 기본 범위에 포함하지 않는다.

샘플 수 N, 모델 수 M, 전체 실행 반복 수 R일 때 본 실험은 `N × 6 × M × R`관측이다. 첫 구현 검증은 R=1로 시작한다. 목표 N=15이면 모델당 90관측, 두 모델이면 180관측이다. N=10~20에서는 모델당 60~120관측이다. R=1 결과로 모델 실행 간 변동성을 추정하지 않는다.

## 3. 수렴·기능·유사도의 측정 계약

### 3.1 거리 d_n의 단위

원본 코드를 x₀, t번째 중간 코드를 yₜ, 출발 언어로 복원된 코드를 xₜ로 정의한다.

```text
x₀(A) → y₁(B) → x₁(A) → y₂(B) → x₂(A) → …
       왕복 1회                 왕복 2회
```

사용자 결정에 따라 $d_n$의 단위는 FPS 크기로 확정한다. 여기서 FPS는 출발 코드부터 번역 중 생성된 서로 다른 코드 상태를 모은 관측 집합이다. 코드 상태는 `(언어, 코드 식별 해시)`로 식별한다. 서로 다른 언어의 소스 문자열이 우연히 같더라도 별개의 상태다.

편도 번역 단계 번호를 j, 그 결과를 zⱼ, 결과 언어를 Lⱼ로 두면 집합과 크기는 다음과 같다.

```text
S₀ = {(A, x₀)}                         # 출발 코드 포함: 크기 1
Sⱼ = Sⱼ₋₁ ∪ {(Lⱼ, zⱼ)}                # 새 상태만 추가
Dⱼ = |Sⱼ|                              # 단계별 FPS 크기
d_n = Dⱼ                               # 근사 고정점 성공 시점의 FPS 크기
```

상태 동일성의 초안은 추출된 코드의 줄바꿈만 LF로 통일한 UTF-8 소스 해시다. 식별자·리터럴·주석·일반 공백·Haskell 들여쓰기·Prolog 항을 임의로 제거하지 않는다. 실제 실행 소스는 별도로 원문 그대로 보관한다. 최종 동일성 규칙은 세 언어 예제로 검증하여 동결한다. 코드 추출에 성공했다면 기능 실패 코드도 관측 상태로 기록하고, 코드 자체를 추출하지 못한 응답은 코드 상태에 추가하지 않는다.

0.85 이상의 유사도는 수렴 판정 기준이며 상태 중복 제거 기준이 아니다. 비슷하지만 정확히 다른 코드는 FPS에서 별개로 센다. 임계값 이상의 유사성은 추이성을 보장하지 않으므로 이를 이용해 상태를 임의로 합치지 않는다. 동일 상태의 재등장, API 재시도, 저장된 응답을 재사용하는 재개는 새 상태를 만들지 않는다.

| 경로 예시 | FPS 크기 | 완료 왕복 수 |
| --- | ---: | ---: |
| `A₀ → B₀ → A₀` | 2 | 1 |
| `A₀ → B₀ → A₁`에서 임계값 도달 | 3 | 1 |
| `A₀ → B₀ → A₁ → B₀ → A₁`에서 두 번째 복원 시 임계값 도달 | 3 | 2 |

완료 왕복 횟수 t와 편도 번역 수 j는 실행량으로 별도 기록한다. d_n을 t, 2t 또는 고정 오프셋으로 환산하지 않는다. 이 계획은 참고 논문의 FPS 크기라는 거리 단위를 채택하되, 코드 상태 동일성과 유사도 임계값에 따른 종료를 새로 명시한 코드 실험이다. 참고 논문의 자연어 문장 일치 방식과 완전히 같은 프로토콜이라고 주장하지 않는다.

### 3.2 유사도 Sym의 비교 대상

유사도는 비교 대상을 명시하여 저장한다.

| 필드 | 비교 | 용도 |
| --- | --- | --- |
| `Sym_adj(t)` | 직전 출발 언어 코드 xₜ₋₁과 현재 복원 코드 xₜ | 반복 종료 판단에 사용하는 유사도 |
| `Sym_origin(t)` | 최초 기준 코드 x₀와 현재 복원 코드 xₜ | 반복 중 원본 표현으로부터의 변화 관찰 |
| `Sym` 또는 `Sym_final` | 성공한 왕복 t*에서의 `Sym_origin(t*)` | 주 결과표에 제시할 성공 조건부 최종 유사도 |

원본과의 유사도 `Sym_origin`가 0.85 이상이라는 사실만으로 수렴을 판정하지 않는다. 수렴 여부는 인접 복원 코드의 `Sym_adj`로 판단하고, 최종 보고에서는 두 값을 별도 열로 제공한다.

새 판정의 공통 분석기 초안은 세 출발 언어 모두에 적용하는 JPlag text 모드다. 기존 Haskell·Prolog의 text 보조 지표 사용 방침을 이어받되, 새 실험의 임계값 판정에는 C++도 같은 모드를 사용하여 분석기 혼합을 피한다. JAR 버전, 최소 매칭 토큰 수, 점수 필드 `averageSimilarity`, 0~1 범위, 전처리·입출력 래퍼 포함 여부를 동결한다. C++ 전용 분석기 점수는 `Sym_native_cpp`라는 별도 보조 열에 둘 수 있으나 text 점수나 수렴 임계값에 혼합하지 않는다.

text 점수는 코드 구조·의미 동등성을 직접 보장하지 않는다. 짧은 코드, 공통 입출력 래퍼, 변수명 변화, 주석·공백 변화 및 연산자·분기 변경에 대한 검사로 적합성을 확인한다. 동일 입력의 반복 측정도 확인한다. 측정 실패나 길이 미달은 NA와 사유로 기록하며 임의로 0이나 1을 대입하거나 다른 분석기로 자동 대체하지 않는다. 공통 분석기가 부적합하면 본 실험 전에 대체 방식과 임계값을 새 설계 버전으로 확정한다.

### 3.3 근사 고정점과 반복 종료

임계값을 θ=0.85로 둔 초안에서, 다음 조건을 모두 처음 만족하는 t를 후보 도달 시점으로 기록한다.

1. t번째까지 생성한 모든 중간 코드와 복원 코드가 기능 검사를 통과했다.
2. `Sym_adj(t)`가 측정 가능하고 `Sym_adj(t) ≥ θ`다.
3. 해당 복원 단계까지의 FPS 크기 Dⱼ가 10 이하이고 별도 실행 예산 안에 있다.

0.85는 예시 임계값이므로 본 실행 전에 확정한다. 임계값은 반올림 전 점수에 적용하며 0.85를 포함한다. 합의된 유사도 임계값에 따른 "근사 고정점"이지, 코드의 완전한 동일성이나 영구적인 고정점을 뜻하지 않는다. 원본·생성 코드의 해시는 FPS 상태 동일성과 무결성을 확인하는 데 사용하고, 근사 수렴은 Sym_adj로 판정한다.

새 기본 규칙은 출발 언어로 복원된 코드의 Sym_adj가 임계값에 처음 도달한 해당 왕복에서 성공 종료한다. 중간 언어의 코드 재등장만으로는 성공 판정을 내리지 않는다. 기존 실험의 추가 5회 확인은 자동으로 이어받지 않는다. 추가 확인을 연구하려면 별도 조건과 예산으로 등록한다.

"거리 10을 넘어가면 중지"는 매 편도 번역 직후 FPS 크기를 갱신하여 판단한다. 새 상태가 추가되어 Dⱼ=11이 되면 해당 코드와 기능 평가를 기록한 뒤 추가 모델 번역을 중지한다. 중간 언어 단계에서 넘었더라도 출발 언어로 복원하기 위한 추가 호출을 하지 않는다. 코드 생성 전에는 새 상태인지 알 수 없으므로 11번째 서로 다른 상태의 관측 자체는 발생할 수 있다. Dⱼ=10에서는 동일 상태가 다시 나올 수 있으므로 즉시 중지하지 않는다.

종료 판정 우선순위는 코드 형식·기능 실패, FPS 상한 초과, 복원 단계의 유사도 측정·임계값 판정 순서다. 상한 초과 여부는 별도 플래그로도 남긴다. Dⱼ=11에서 유사도가 높아도 성공으로 인정하지 않는다. 성공 시 d_n은 실제 FPS 크기이고, 미수렴·실패의 성공 조건부 d_n은 NA다. 종료 시 관측한 `fps_size_at_stop`(예: 11)은 실제 측정값으로 별도 보고하며, 이를 수렴에 성공한 거리로 섞지 않는다.

FPS는 같은 상태를 반복하면 증가하지 않으므로 이것만으로 무한 반복을 막을 수 없다. 별도 운영 예산 `max_translation_steps=20`을 초안으로 두고 시간·재시도 제한과 함께 본 실행 전에 확정한다. 이는 최대 20회 편도 번역이라는 실행량 제한이며 거리 10과 같은 개념이 아니다. 이 예산에 도달하면 `translation_budget_reached`로 구분하고 d_n은 NA로 둔다.

### 3.4 기능 성공률 P_sf와 실패 처리

이 계획에서 $P_{sf}$는 "기능을 보존하며 임계값 수렴에 성공한 비율"로 정의한다. 평가 가능한 관측 중 3.3절의 세 조건을 모두 만족한 관측의 비율이다.

`P_sf = 기능 검사와 임계값 수렴을 모두 통과한 관측 수 / 평가 가능한 관측 수`

단순한 테스트 통과율과 구별하기 위해, 종료 시점까지 생성된 모든 단계가 기능 검사를 통과한 비율은 `P_functional`로 별도 기록한다. 예를 들어 기능 검사는 모두 통과했지만 임계값 도달 전에 FPS 상한이나 별도 번역 예산에 도달한 관측은 P_functional의 성공, P_sf의 실패다. 필요할 때 단계별 테스트 통과 수와 비율도 함께 제시한다.

| 종료 유형 | P_sf 집계 | d_n·최종 Sym |
| --- | --- | --- |
| 기능 통과 + 임계값 도달, FPS ≤ 10 | 분모·분자 포함 | 도달 시 FPS 크기와 원본 대비 유사도 |
| 형식·컴파일·실행·오답·시간 초과 | 분모 포함, 분자 제외 | 성공 조건부 값은 NA |
| FPS 크기 10 초과 | 분모 포함, 분자 제외 | NA; 실제 종료 FPS 크기는 별도 기록 |
| FPS ≤ 10이지만 별도 번역 예산 도달 | 분모 포함, 분자 제외 | NA; 실행량과 FPS 크기를 별도 기록 |
| 유사도 도구 오류·측정 불가 | 별도 미평가 건수·사유 공개 | NA; 본 집계 완결 전에 원인 검토 |
| 인증·API·도구 부재 등 인프라 오류 | 별도 미평가 건수·사유 공개 | NA |
| 진행 중·중단·미완료 | 완료 결과에 포함하지 않고 별도 공개 | NA |

분모에는 생성 코드로 인한 실패를 포함하고 인프라 실패와 혼합하지 않는다. 모든 표에 계획 수·평가 수·성공 수·실패 수·미평가 수·미완료 수를 함께 제시한다. 기능 오류는 최초 실패에서 종료하고, 유사도가 높아도 성공으로 바꾸지 않는다. 실패 시점의 측정 가능한 유사도는 진단용으로 보존하되 성공 조건부 Sym과 합산하지 않는다.

### 3.5 실행 순서와 기록

```text
원본의 세 언어 기준 코드 검증
각 문제·방향·모델 관측에 대해:
  FPS에 출발 코드 상태 추가: 크기 1
  별도 편도 번역 예산이 남아 있는 동안 A → B, B → A를 교대로 수행
    코드를 추출할 수 없으면 형식 실패로 종료
    (언어, 코드 해시)를 FPS에 추가; 중복은 추가하지 않음
    생성 코드의 모든 평가 입력 검사
    형식·기능 실패이면 실패 종료
    출발 언어 A의 복원·평가를 완료했으면 완료 왕복 수 증가
    FPS 크기 > 10이면 max_distance_reached로 종료
    출발 언어 A로 복원한 단계에서:
      Sym_adj와 Sym_origin 측정
      유사도 판정이 불가능하면 별도 오류로 중단
      Sym_adj ≥ θ이면 d_n=현재 FPS 크기로 성공 종료
  예산 소진까지 성공하지 못하면 translation_budget_reached로 종료
```

비인접 코드의 재등장은 FPS 증가 없이 진동 진단으로 기록하며 별도 실행 예산으로 무한 반복을 막는다. 재개 시 저장된 코드 상태로 FPS를 복원하고, 이미 완료한 번역·평가·유사도 측정을 재사용한다. 상태별 최초 등장 단계·언어·해시, 중복 참조, 단계별 FPS 크기와 왕복 번호를 저장하여 계수를 감사할 수 있게 한다.

## 4. 공통 샘플 10~20개 선별

목표는 15개이며, 실제 세 언어 검증을 통과한 공통 문제 집합을 최소 10개·최대 20개로 확정한다. 세 언어 중 하나라도 구현·검증이 불가능한 문제를 다른 언어 경로에서만 사용하지 않는다. 10개 미만이면 문제 후보를 보완한 뒤 본 실행으로 진행한다.

| 영역 | 후보 과제 예시 | 목표 개수 |
| --- | --- | ---: |
| 수치·조건 | 최대공약수, 소수 판정, 자릿수 계산 | 3 |
| 문자열 | 회문, 문자 빈도, 문자열 변환 | 3 |
| 리스트·집합 | 정렬, 중복 제거, 집합 연산 | 3 |
| 재귀·동적 계획 | 피보나치 변형, 계단 수, 격자 경로 | 3 |
| 탐색·관계 | 연결성, 경로 탐색, 제약 탐색 | 3 |

위 표는 후보 영역이며 실제 선별 완료 목록이 아니다. 현재 `problem/`의 자료를 우선 검토하고 다음 기준으로 선정한다.

- 외부 네트워크·GUI·난수·운영체제 종속 기능 없이 단일 프로그램으로 실행할 수 있다.
- 세 언어가 같은 문제 명세·입력 범위·출력 계약·정답 판정·평가 입력을 사용한다.
- 정수 범위, 정렬 순서, 중복 해, Prolog의 해 선택과 출력 순서를 명세로 고정한다.
- 출력 길이, 재귀 깊이, 탐색량을 제한하여 도구·언어별 자원 제한을 사전에 검증한다.
- 기준 코드는 입출력 래퍼만으로 구성된 과도하게 짧은 예제를 피하고, 표준 라이브러리 사용 기준을 통일한다.
- 번역 결과나 특정 모델의 성공률을 보고 쉬운 문제만 남기지 않는다. 제외 사유는 번역 실행 전에 기록한다.

문제별로 C++·Haskell·Prolog 기준 코드 3개를 준비한다. 서로 다른 언어의 관용적 표현은 허용하되 알고리즘·자료 표현의 주요 차이를 주석 문서에 기록한다. 언어 효과와 초기 표현의 효과가 완전히 분리된다고 주장하지 않는다.

공개 예제와 별도로 문제당 최소 10개 평가 입력을 준비하고, 기존의 검증된 13개 입력이 있으면 재사용을 우선한다. 경계값·반복값·정상값·명세가 허용하는 빈 입력을 포함한다. 기준 코드 3개가 모두 같은 정답을 출력하는지 확인하고, 선정 목록·코드·평가 입력·도구 버전의 해시를 동결한다.

### 5.1 모델·제공자 공통 계약

1. 공통 번역 요청은 출발/대상 언어, 문제 명세, 공개 예제, 현재 코드, 모델·생성 설정을 받는다.
2. 공통 응답은 생성 텍스트, 추출 코드, 실제 모델 식별자, 종료 사유, 토큰 사용량, 지연 시간, 원본 응답 참조를 제공한다.
3. LM Studio 어댑터를 유지하고, 별도 endpoint의 호환 HTTP API를 사용할 수 있는 어댑터를 추가한다. 비호환 API는 같은 계약의 별도 어댑터로 확장한다.
4. provider와 모델명을 분리한다. 같은 LM Studio의 모델 변경과 서버·API 제공자의 변경은 별도 조건이다.
5. endpoint, 모델, 인증용 환경변수 이름, 요청 제한 시간, 재시도 상한을 설정으로 받는다. 키 값·Authorization 헤더는 로그·설정 사본에 저장하지 않는다.
6. seed·temperature·top_p·최대 출력 길이 등의 지원 여부를 검사한다. 지원하지 않는 옵션을 조용히 무시하지 않고, 거부하거나 미지원 사실과 실제 적용 조건을 명시한다.
7. 제공자가 보고하지 않는 토큰 사용량·양자화·내부 모델 버전은 0이나 추정값으로 채우지 않고 미제공으로 저장한다.
8. 기술적 재시도와 생성 코드 실패를 구분한다. 인증 오류·잘못된 설정은 즉시 알리고, 일시 오류만 정해진 횟수 내에서 재시도한다.
9. 설정·모델·데이터·프롬프트·유사도 정책이 달라진 실행은 이전 관측에 이어 붙이지 않는다.

기존 설정의 `lmstudio` 블록은 호환 입력으로 지원하고 공통 설정으로 변환한다. 새 provider에서도 기존 블록을 필수로 요구하지 않는다. 과거 해시 기반 실행은 기존 정책으로 읽고, 새 실험은 별도 experiment_version과 출력 디렉터리로 구분한다.

새 설정에 필요한 필드는 다음과 같다. 필드명은 구현 전 확정할 설계안이며 현재 CLI에서 이미 동작한다는 뜻은 아니다.

| 영역 | 설계 필드 |
| --- | --- |
| 실험 | experiment_version, problem_ids, seed_language, target_languages, repeats |
| LLM | provider, endpoint, model, api_key_env, generation, request_timeout, retries |
| 판정 | distance_unit=fps_size, state_identity_policy, convergence_policy, similarity_backend, similarity_mode, threshold, max_fps_size=10 |
| 반복 보호 | max_translation_steps, 관측 시간 상한, 재시도 상한; FPS 제한과 별개 |
| 실행 | 언어별 도구 경로, compile_timeout, fixture_timeout, output_root |
| 재현 | 프롬프트·코드·입력·설정 해시, 적용된 옵션과 미지원 옵션 |

## 6. 실행 단계와 예산

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1. 정의 확정 | d_n 단위, Sym 비교 대상·분석기, P_sf 분모, 임계값·종료 우선순위 확정 | 재현 가능한 측정 계약과 설정 초안 |
| 2. 샘플 검증 | 공통 문제 10~20개와 언어별 기준 코드·평가 입력 준비 | 모든 문제의 세 기준 코드 검증 통과 |
| 3. 라이브러리 개선 | provider 분리, 세 출발점, 단계별 유사도 판정, 저장·재개 구현 | 핵심 경계 검사와 기존 기능 회귀 검사 통과 |
| 4. 예비 실행 | 선정 집합의 대표 3문제 × 6경로 = 모델당 18관측 | 기능 실패·유사도·종료·응답 보존·비용 점검 |
| 5. 설계 동결 | 최종 샘플·모델·실행 반복·임계값·프롬프트·예산 확정 | 미정 필드가 없고 예비 관측과 본 관측 분리 |
| 6. 본 실행 | 모든 공통 문제·방향·모델을 동일 정책으로 실행 | 계획 관측 수와 종료·미평가·미완료 수 대조 |
| 7. 분석·문서화 | 세 지표·실패·방향·모델 차이와 실제 코드 사례 분석 | 원본과 표·그림 대조, 재생성 및 해석 검토 |

본 실험의 예비 사용 문제를 식별하고, 그 문제를 제외한 민감도 분석도 제공한다. 예비 관측 자체는 본 결과에 합산하지 않는다. 모델 간 비교는 동일한 본 문제 집합을 사용한다.

FPS 크기만으로 모델 호출 수를 계산할 수 없다. 매 단계 새 상태가 나오면 초기 상태 1개에서 편도 번역 10회 후 FPS=11로 중지하지만, 중복 상태가 나오면 더 많은 번역이 필요할 수 있다. 별도 운영 예산을 관측당 편도 20회로 채택할 경우 N=15, M=2, R=1에서 본 실험 최대 3,600회, 예비 최대 720회다. 이는 FPS를 두 배 한 계산이 아니라 별도 호출 예산에 따른 상한이다. 조기 종료와 API 재시도는 따로 집계한다. 최종 호출·토큰·요금·시간 예산은 예비 실측과 모델 조건으로 동결한다. 기능 실패를 성공할 때까지 다시 생성하지 않는다.

첫 완결 실험은 LM Studio의 기준 모델로 수행하고, 다른 LLM의 동일 프로토콜 실행을 추가한다. 두 번째 모델과 endpoint는 접근 가능성·지원 옵션·예산을 확인해 예비 단계에서 확정한다. 라이브러리의 다른 provider 지원은 모의 응답 검사와 실제 연결 점검을 구분하여 보고한다.

## 7. 분석 계획

- 모델별 6개 방향에 대해 P_sf의 성공/평가 수와 95% 구간을 보고한다. P_functional과 미평가·미완료 수를 함께 제시한다.
- 성공 조건부 d_n과 Sym_final의 표본 수·중앙값·사분위 범위를 보고하고, 판정에 사용한 Sym_adj도 별도로 제시한다.
- 같은 문제의 반대 방향 3쌍과 같은 경로의 모델 차이를 대응 비교한다. 성공률은 평가 가능한 공통 문제, 거리·유사도는 공통 성공 문제를 사용한다.
- 문제 단위로 모든 경로를 함께 재표집하는 bootstrap을 사용하며, 비교 목록·재표집 횟수·난수 seed·다중 비교 처리를 본 실행 전에 확정한다. 기본안은 2,000회와 비교군별 Bonferroni 구간이다.
- 작은 표본이나 성공 0건으로 퇴화하는 구간을 명시한다. 성공률에는 Wilson 구간도 제공하고, 조건부 표본이 없으면 거리·유사도를 NA로 표시한다.
- 유사도 임계값 0.80·0.85·0.90의 변화는 별도 민감도 조건으로 검토한다. 조기 종료한 기록으로 더 높은 임계값 도달 시간을 추정하지 않는다. 0.90 조건이 필요하면 별도 관측 또는 사전 등록한 충분한 궤적이 필요하다.
- 컴파일·실행·오답·시간 초과·상한 도달·유사도 미측정·인프라 오류를 구분하고, 실패가 중간 언어와 복원 중 어디에서 발생했는지 분석한다.
- 성공·실패 사례를 사전에 정한 규칙으로 선택하여 재귀·반복·상태·규칙·입출력 처리의 실제 변화를 검토한다.

그림은 방향별 P_sf, 성공 조건부 d_n 분포, Sym_final 분포, 반복별 Sym_adj 궤적을 기본으로 한다. 세 지표를 하나의 가중 거리 점수로 합치지 않는다. 단일 모델 결과를 언어 자체의 거리나 패러다임의 인과 효과로 일반화하지 않는다.
