# v2 데이터·프롬프트의 논문 적합성 검토

검토일: 2026-09-17. 대상은 `lmstudio_v2.yaml`의 40문제와 실제 RTT 프롬프트 조립·평가 코드다. 최종 코퍼스와 조건은 `v2-a-quality-1`로 구분한다.

## 판정과 사용 범위

개선된 자료는 "고정한 40개 표준입출력 과제에서 반복 번역의 기능적 생존과 구조 변화를 관찰하는 탐색 실험"에 사용할 수 있다. 아래의 실행·형식 검증은 통과했다. 모델별 번역 난이도와 성공률은 아직 측정하지 않았으므로 본 실험 완료나 범용 벤치마크 타당성 확보로 표현하지 않는다.

문제 자체의 알고리즘 난이도, 특정 테스트 입력이 요구하는 자원, 언어 간 번역 난이도는 구별해야 한다. 소스 코드가 주어지는 번역 과제이므로 어려운 알고리즘 문제를 푸는 능력과 같은 것을 측정하지 않는다. 이 자료는 의도적으로 선정한 표본이며, 전체 문제 모집단의 난이도 분포를 대표하지 않는다.

## 확인된 문제와 개선

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 평가 규모 | 문제당 10쌍, 총 400쌍. 작은 입력 비중이 큼 | 기존 400쌍 보존 + 문제당 3쌍, 총 520쌍 |
| 큰 입력 | 일부 수치 상한만 확인, 대부분 짧은 배열·문자열·작은 그래프 | 큰 배열·문자열, 깊은 그래프, 큰 DP 값과 수치·용량 경계 추가 |
| 설명 형식 | IPOP 서사·다중 예제와 LeetCode 요약 형식이 혼재 | 양쪽 모두 과제 요약·제약·입출력 계약 중심, 별도 예제 한 쌍 |
| 설명 길이의 예 | IPOP_1620 명세 3,004자 | 동일 입출력 계약을 보존한 399자 요약 |
| 지시 범위 | P1에 "제공된 예제"의 동작 보존이라는 문구 | P2는 명세의 모든 유효 입력에 대한 동작 보존을 요구 |
| 공백 처리 | 프롬프트 조립에서 `strip()`, 입력 중복 검사에서 공백 토큰화 | P2 예제 원문 보존, LC_0003은 줄 끝 개행만 제거한 키로 중복 검사 |
| 검증 범위 | 평가 입력 위주로 검증 | 저장된 예제 211쌍도 검증. 중복 제거 시 91쌍 |
| 변경 추적 | 설명·테스트 변경을 동일 조건으로 섞을 위험 | 변경 전 스냅샷, 새 코퍼스·프롬프트 버전, 별도 출력 디렉터리 |

원래 기준 코드 40개, 평가 400쌍, 실제로 프롬프트에 제공하는 첫 예제 40쌍은 바이트 단위로 보존했다. 입력·정답을 모델 실패를 보고 수정하거나 문제를 교체하지 않았다. IPOP의 보관된 원문 공개 예제 전체와 LeetCode 공개 예제 51개를 평가 입력에서 제외한다.

작은 테스트 집합만으로 코드의 기능적 정확성을 판단하면 오류를 놓칠 수 있다는 검토 방향은 [EvalPlus 논문](https://arxiv.org/abs/2305.01210)을 참고했다. 이번 13쌍 구성은 해당 논문과 같은 규모·절차를 재현한 것이 아니며, 그 연구의 결과를 이번 데이터의 품질 보증으로 사용하지 않는다.

## 난이도와 구성

공식 플랫폼 등급이나 모델 통과율 대신 코드의 알고리즘 구조를 기준으로 다음과 같이 분류했다. 이는 연구자가 정한 설명용 분류다.

| 구조 분류 | 문제 수 | 해석 |
|---|---:|---|
| 단순 순회·정렬·순서 탐색 중심 | 14 | 문자열 순회, 빈도, 정렬, 위치 탐색, 정수 연산 등 |
| 상태 유지·DP·그래프 처리 중심 | 23 | 상태 갱신 순서, 자료구조, 경계 인덱스, 다중 질의 등의 보존이 필요 |
| 재귀·조합 탐색 중심 | 3 | 하노이, 쿼드트리, N-Queen. 재귀 구조·출력 순서·탐색 범위가 중요 |

이 분류는 쉬움·보통·어려움의 검증된 순서 척도가 아니다. 실제 난이도를 논문에서 논하려면 모델별 최초 번역 통과율·최초 실패 유형·입력 범주를 예비 실험에서 측정해야 한다. 이를 보고 문제를 사후 교체하면 선택 편향이 생기므로 예비용 표본과 주 분석 표본을 구분한다.

이분탐색, 격자 DP, 단조 스택, 문자 빈도, 슬라이딩 윈도, 그래프 도달성에 중복 문제군이 있다. 현재 기록한 묶음은 32개이며 모든 의미적 중복을 완전히 분리했다는 뜻은 아니다. [문제별 CSV](../problem/metadata/quality/problem_profile.csv)에 분류와 입력 크기를 기록했다. 과제 40개를 독립 단위로 삼되 문제군 묶음에 따른 민감도도 보고한다. 테스트 520개나 동일 문제의 반복 실행을 독립 과제 520개로 세지 않는다.

## 추가 입력의 설계

추가 입력은 문제별 독립 난수열 `Random(20260917 + 문제 번호)`와 사전에 정한 경계 패턴으로 생성했다. 일반적으로 두 기능 입력과 한 규모 입력을 추가했다. 하노이·N-Queen·666 수 등 작은 정수 하나가 입력인 과제는 고정된 미사용 값을 사용한다. 공백 문제에는 앞뒤 공백과 연속 공백 입력을 명시적으로 추가했다.

| 범주 | 대표 내용 |
|---|---|
| 배열·문자열 크기 | LC_0053·LC_0387·LC_0739 100,000개/자, LC_0912 50,000개, IPOP_9935 1,000,000자 |
| 사전·정렬·좌표 | IPOP_1620 이름·질의 각 100,000개, IPOP_2110 집 200,000개, IPOP_18870 좌표 100,000개 |
| 그래프·격자 | LC_0207 정점 2,000개 장주기 순환, LC_0547 정점 200개, LC_0064 200×200 격자 |
| 수치와 중간 상태 | LC_0053 합 10^9, LC_0062 큰 경로 수, LC_0518·LC_0063의 큰 중간 계산과 최종 0 |
| 재귀·출력 | 하노이 N=12,14,16; N-Queen N=12,13,14 |

전 문제의 모든 최대 크기를 검사한 것은 아니다. 하노이 최대 N=20과 좌표 압축 최대 N=1,000,000은 이번 추가 입력에서 다루지 않는다. N-Queen은 유효 범위 1..14 중 공개 예제 N=8을 제외하면 서로 다른 평가 입력을 최대 13개만 만들 수 있어 현재 13개가 전체 미제시 정수 영역이다.

큰 입력의 독립 정답 계산을 가능하게 하려고 일부 완전탐색 검증기를 다른 정확 알고리즘이나 메모이제이션으로 확장했다. 작은 입력의 전수 검사, 양방향 순회·누적합·계수 정렬·반복 DFS·비트셋 LCS 등의 대조 방법을 문제별 manifest에 기록했다. 균등 간격 공유기 배치는 수학적 상한으로, 큰 N-Queen은 별도 계산과 [OEIS A000170](https://oeis.org/A000170/b000170.txt)의 공개 계수로 확인했다.

## 실제 검증 결과

| 검사 | 결과 |
|---|---:|
| 평가 입력 제약·고유성·독립 정답 확인 | 520/520 |
| C++17 기준 코드의 평가 실행 | 520/520 |
| 저장된 프롬프트 예제 실행 | 211/211, 고유 입력·정답 쌍 91개 |
| 대응 외부 JavaScript 평가 실행 | IPOP 3문제 39/39, LeetCode 21문제 273/273 |
| LeetCode 공개 프롬프트 예제의 외부 JS 실행 | 21/21 |
| 진단 오류 코드 검출 | 기존 입력 1/8 → 확장 입력 8/8 |

진단 패널에는 16비트 정수로 누적합·인덱스·거리·DP 값을 저장하는 오류, 64/256/1024 크기만 처리하는 오류, 의미 있는 공백을 제거하는 오류를 넣었다. 8개는 이 감사에서 선정한 가상 오류이며 실제 LLM 오류의 무작위 표본이 아니다. 검출률 100%를 전체 오류 탐지율이나 의미 동치 보장으로 표현하지 않는다. [코드와 사례별 검출 기록](../problem/metadata/quality/audit_report.json)을 함께 공개한다.

## 프롬프트와 실험 조건

P2는 모든 유효 입력의 동작, 표준입출력, 공백, 정수 범위, 인덱스, 출력 순서를 보존하도록 지시한다. 언어별 알고리즘 힌트나 평가 입력은 제공하지 않는다. Java의 `Main` 요구는 실행기 진입점 계약이다. 문자열의 빈 줄·앞뒤 공백도 예제에서 유지한다. LC_0003의 문자 범위는 현재 [공식 명세](https://leetcode.com/problems/longest-substring-without-repeating-characters/description/)를 확인했으며 인쇄 가능한 ASCII로 제한한 어댑터 범위를 명시했다.

프롬프트 길이는 실제 모델 토큰 수가 아닌 문자 수로만 기록했다. 실제 토크나이저의 입력 길이·context limit과 4,096 출력 토큰 상한의 적절성은 모델별 예비 실행에서 별도로 점검해야 한다. 첫 순방향 요청 120개는 [프롬프트 스냅샷](../problem/metadata/quality/prompt_previews/)에 보관한다. 역방향 요청에는 각 모델의 실제 중간 코드가 필요하다.

P1과 P2, 원래 설명과 요약 설명은 서로 다른 조건이다. 이전 실험과 차이가 나더라도 테스트 강화만의 효과로 단정하지 않는다. 테스트 효과를 분리하려면 동일한 생성 코드를 원래 400쌍과 추가 120쌍에 각각 재평가하고, 프롬프트 효과는 같은 코퍼스·모델·디코딩 조건의 별도 대응 실험으로 비교한다.

## 논문에 남길 한계와 실행 전 확인

- 40문제의 의도 표본이며 고난도·현실 소프트웨어·Unicode·부동소수·동시성 등을 포괄하지 않는다. 유명 공개 문제이므로 학습 오염이 없다는 주장은 할 수 없다.
- 유사 문제군이 있어 40개가 모두 독립적인 알고리즘이라는 가정은 강하다. 경로별 성공 집합의 구성 차이와 문제 단위 불확실성을 보고한다.
- 문제당 13개 유한 입력의 통과는 의미 동치의 증명이 아니다. 대규모 퍼징이나 독립적으로 보관한 후속 평가 집합은 아직 없다.
- 큰 입력의 timeout은 언어별 실행 속도·구현 전략의 영향을 받는다. 30초 제한 아래의 운영적 성공과 순수한 기능 오류를 구분하고 실패 범주·사례를 공개한다. 이 자료만으로 성능 등가성이나 점근 복잡도 요구 충족을 판정하지 않는다.
- Two Sum의 인덱스 정렬, boolean의 1/0, 함수형 문제의 stdin/stdout 변환은 원 명세와 다른 평가 계약이다. 어댑터 계약을 부록에 명시한다.
- 개선된 데이터로 LLM 번역 실험은 실행하지 않았다. 본 실험 전에 실제 모델과 3개 대상 언어에서 자원·길이·오류 분류를 점검하고 조건을 동결해야 한다.

## 논문 방법 절에 사용할 수 있는 문장

본 연구는 IPOP 19개와 LeetCode 21개로 구성된 40개의 표준입출력 변환 과제를 사용하였다. 각 과제에는 공개 예제와 겹치지 않는 평가 입력 13개를 마련하여 총 520개 입력·정답 쌍을 구성하였다. 기존 400쌍을 유지하면서 고정 seed 기능 입력과 크기·수치 경계 입력 120쌍을 추가하였다. 정답은 별도 구현, 작은 입력의 완전탐색 또는 명시한 수학적 근거로 교차 확인하고 C++17 기준 코드로 실행 검증하였다. 번역 프롬프트에는 과제의 입출력 계약, 고정된 예제 한 쌍과 번역 대상 코드만 제공하며 평가 입력·정답·진단 정보를 제공하지 않는다. 이 평가는 선정한 유한 입력 집합에서의 기능적 생존을 측정하며 프로그램 의미 동치나 문제 모집단 전체에 대한 일반화를 주장하지 않는다.

실험을 실제로 수행하기 전에는 위 문장에서 결과·성공률을 추가하지 않는다. 재생성·재검증 명령과 산출물은 [품질 점검 안내](../problem/metadata/quality/README.md)에 있다.
